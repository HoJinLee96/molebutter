# 실제 보유 재고·매입 관리

`/inventory`에서 구매 주문, 보유 재고, 미입고 수량과 입출고 이력을 관리한다. 기존 상품의 외부 매입처 가격·재고 조회와 별개다. 외부 조회 결과에서 보유 재고를 자동 생성하거나 변경하지 않는다.

## 등록과 사용

관리자는 매입일과 하나 이상의 구매 항목(기존 상품, 주문 수량)을 등록한다. 상품 정보는 현재 연결 상품의 이미지·브랜드·상품코드를 사용한다. 구매 당시 코드·상품명은 저장하지 않는다. 색상·사이즈는 공백도 허용한다. 상품 목록에서는 **재고 조회** 버튼으로 재고 페이지에 진입한다. 매입처 판매글의 **매입 등록** 링크는 연결 상품만 미리 선택하며 실제 구매처를 대신 채우지 않는다. 상품 찾기는 내부 등록 상품 DB를 검색하고 이미지·브랜드·상품코드를 보여주는 선택 모달을 연다. 네이버 검색이나 외부 최신화를 실행하지 않는다.

동일 상품을 여러 단가로 구매하면 매입 항목을 분리한다. 주문별 구매처·주문번호·주문서 URL·결제 수단·결제일·결제 메모를 기록한다. 수동 결제 금액 입력 대신 `Σ(주문 수량 × 단가)`인 매입 합계를 즉시 표시한다. 단가가 하나라도 미입력이면 합계는 미확인이며 입력한 0원은 정상 계산한다. 화면은 BigInt, 서버는 정확한 정수 계산을 사용한다. 관리자용 주문 목록·상세의 `purchaseAmount`는 원 단위 정수 문자열 또는 null이며 별도 저장하지 않는다. 주문 수량·단가 수정은 합계를 바꾸지만 입출고·미입고 취소·환불은 합계를 바꾸지 않는다. 기존 `paymentAmount`와 입력 API는 호환성을 위해 유지하며 저장된 값은 상세의 ‘기존 입력 결제 금액’으로 표시한다. 새 화면의 구매 정보 수정은 이 값을 보존한다. 배송비 배분·할인·세금·판매 수익 계산은 제공하지 않는다. 원화와 정수 개수를 사용한다. `단가 × 보유 수량`은 입력 단가 기준 잔여 금액이다. 날짜 동일 체크 중 결제일은 매입일과 동기화된다. URL에서 알려진 쇼핑몰 호스트만 로컬 분석하며 직접 입력한 구매처는 덮어쓰지 않는다.

등록 모달은 최대 1,240px이며 구매 항목을 상품 정보·색상·사이즈·주문 수량·단가·상품 메모 순서로 배치한다. 화면 너비 1,100px 미만에서는 2열, 640px 미만에서는 1열이다. 결제 메모와 상품 메모는 최대 2,000자의 한 줄 입력을 사용하며 기존 여러 줄 메모를 직접 수정하지 않은 경우 원문을 보존한다.

주문 등록은 미입고 수량만 생성하며 초기 입고를 함께 제출하는 요청은 거절한다. 이미 받은 물건도 주문 저장 후 구매 주문 상세의 항목별 입고 버튼으로 등록한다. 입고일시는 현재 한국 시간을 기본값으로 제공한다. 부분입고는 날짜별로 기록하고 미입고 취소는 관리자만 처리한다. 입고는 미입고를 차감하고 보유를 늘린다. 보유 재고 탭에는 구매 주문이 있는 상품을 코드별 한 행으로 표시한다. 입고 전에도 보유 0·미입고 수량을 보여주고, 보유·미입고가 모두 0이 되어도 재고 없음 상태로 유지한다.

구매 주문 목록의 각 행에서는 주문 상세 오른쪽에 ‘입고 확인’을 제공한다. 미입고가 0이면 비활성화한다. 모달은 주문의 미입고 상품별 코드·색상·사이즈·잔량을 보여주며 각 상품의 수량과 입고 확인 버튼으로 해당 상품만 입고한다. 입고 수량 기본값은 잔량이며 공통 입고일시는 현재 한국 시간으로 제공하고 수정할 수 있다. 입고 후 잔량·목록을 갱신하고 완료한 상품은 대상에서 제외한다. ADMIN과 PRODUCT가 사용하며 모달에는 결제·단가 정보를 표시하지 않는다. 기존 항목별 이동 API를 사용하고 새 API나 스키마는 추가하지 않는다. 버전 충돌이면 최신 잔량을 조회해 재확인하도록 안내하고, 통신 실패로 같은 입력을 재시도하면 요청 ID를 유지한다.

보관 위치 개념은 화면·응답·저장 구조에서 제거했다. 입고에서는 수량과 입고일시만 기록한다.

일반 입출고 유형 선택 폼은 제공하지 않는다. 화면은 입고·미입고 취소·이력의 기록 취소를 제공한다. 판매·반품·폐기·실사의 전용 화면은 후속 기능이며 기존 API와 관련 이력은 보존한다. API의 판매 출고·매입 반품·폐기는 보유를 차감한다. 고객 반품은 취소되지 않은 판매 출고를 참조하고 남은 반품 가능 수량만 되돌린다.

실사 정정과 기록 취소에는 사유가 필요하다. 기록 취소는 원수량 전체를 반대로 기록하며 원기록을 삭제하지 않는다. 반품이 남은 판매 출고는 반품 기록을 먼저 취소해야 한다. 취소 때문에 음수 보유·미입고 초과가 발생하면 관련 기록을 먼저 정정한다. 주문 수량 변경도 증가·감소 기록을 남긴다. 매입 반품 환불은 재고와 별도로 NONE/PENDING/COMPLETED를 관리하고 완료 시 금액·날짜를 입력한다. 반품 기록을 취소하려면 환불 기록을 먼저 해제한다.

## 상세 조회와 수량 의미

‘매입 주문 상세’에서 주문 정보와 매입 상품을 함께 조회·수정한다. 별도의 매입 상품 상세 모달은 제공하지 않는다. 재고의 매입 내역과 이력에서 ‘주문에서 보기’를 누르면 해당 주문을 열고 선택한 상품으로 이동하며 이력을 펼친다.

상단 매입 합계·결제 수단·결제 메모를 한 행에 표시한다. 주문 전체와 각 상품의 주문 수량·입고된 수량·미입고 수량도 한 행에 표시한다. 상품 정보·주문 수량·색상·사이즈·관리자용 단가·상품 메모·수정 버튼을 한 행에 배치하며 좁은 화면에서는 2열·1열로 전환한다. 이미지·입력·버튼의 아래선을 맞춘다.

처음에는 읽기 전용이며 주문 정보와 상품별로 각각 수정·저장·취소를 제공한다. 수정 중에는 다른 작업을 막아 입력이 지워지지 않도록 한다. 상품별 수정은 기존 매입 항목 API와 버전 검사를 사용하고 수량 변경은 관련 입출고 원장을 유지한다. 충돌 시 작성한 값을 보존하고, 취소하면 최신 저장값을 조회한다. ADMIN은 주문 정보·주문 수량·단가를 수정하며 PRODUCT는 색상·사이즈·상품 메모를 수정한다. 기존 결제액·별칭과 직접 수정하지 않은 여러 줄 메모는 보존한다. 상품마다 독립 페이지 처리하는 입출고 이력을 펼쳐 확인하고 기록 취소·환불 관리를 실행할 수 있다. 삭제된 주문은 조회만 허용한다.

`receivedQuantity`는 취소되지 않은 RECEIPT 기록의 누계이고 `cancelledQuantity`는 취소되지 않은 CANCEL_PENDING 기록의 누계다. 별도 수량 컬럼 없이 이력에서 계산한다. 항목 목록·상세와 구매 주문 목록·상세에 제공하며 주문에는 상품별 합계를 제공한다. `orderedQuantity = receivedQuantity + pending + cancelledQuantity`를 유지한다. 화면에서는 주문 수량·입고된 수량·미입고 수량을 표시하고 미입고 취소는 양수일 때만 추가한다.

예를 들어 주문 10개·입고 8개·판매 3개이면 입고 누계 8개·미입고 2개·실제 보유 5개다. 판매·매입 반품·고객 반품·폐기·실사 정정은 구매 입고 누계를 바꾸지 않는다. 구매 입고 취소는 입고 누계를 줄이고 미입고를 복원하며 미입고 취소의 기록 취소는 취소 누계를 줄이고 미입고를 복원한다. 보유 재고·잔여 금액·삭제 제한은 계속 실제 보유 수량을 사용한다.

## 상품 단위 보유 재고

보유 재고는 현재 연결 상품코드를 앞뒤 공백 제거·대문자로 통일해 합산한다. 과거 중복 등록 상품도 같은 코드면 한 행이며, 코드가 없는 과거 상품은 내부 상품 ID로 구분한다. 매입 항목 ID는 집계 키가 아니다. 대표 정보는 통합되지 않은 등록 상품 중 삭제되지 않은 상품을 우선하고 가장 작은 ID의 이미지·브랜드·현재 코드를 표시한다.

목록은 상품 정보·보유·미입고·상태·관리자용 잔여 재고 금액·상세로 구성한다. 잔여 금액은 각 항목의 단가 × 보유 수량 합계인 정수 문자열이다. 보유 중 단가 미입력 항목이 있으면 null, 전체 보유가 0이면 문자열 0이다. 평균·대표 단가는 제공하지 않는다. 기본 100개, 코드 오름차순이며 검색·페이지 건수는 그룹 기준이다. 매입 내역의 일부만 검색에 맞아도 전체 그룹 수량을 보여준다.

재고 페이지 상단에는 페이지 이동과 무관한 전체 실제 보유 수량을 표시한다. 보유 재고에서 검색어·브랜드·상품 진입 필터를 적용하면 검색 결과 전체의 보유 수량도 함께 표시한다. 미입고 수량과 삭제된 구매 주문은 보유 합계에 포함하지 않는다. 합계는 서버가 전체 데이터에서 계산해 정수 문자열로 반환하며 화면은 BigInt로 표시한다.

브랜드 선택은 공통 설정의 브랜드와 ‘전체 브랜드’, ‘미지정’을 제공한다. 보유 재고는 표시용 대표 상품의 브랜드로 그룹을 필터링하고 그룹 전체 수량을 유지한다. 구매 주문은 선택 브랜드의 상품이 하나라도 포함된 주문을 표시하며, 입출고 이력은 기록에 연결된 현재 상품 브랜드를 적용한다. 기본 100개는 유지하며 검색어 입력은 데스크톱에서 20rem, 브랜드 12rem, 페이지 크기 6.5rem로 줄인다.

상품 재고 상세는 상품 전체 요약·색상/사이즈별 수량·매입 내역·상품 전체 이력을 제공한다. 매입 내역과 이력은 각각 20개씩 독립 페이지 처리하며 해당 주문의 매입 상품으로 이동한다. 수정과 수량 기록은 매입 항목에 적용하고 모든 합계를 갱신한다. 대표 메모·단가로 다른 매입 건을 덮어쓰지 않는다. PRODUCT에는 금액을 응답하지 않는다.

상품코드 수정은 표시 그룹을 바꾸고 상품 통합은 이동된 참조에 따라 합산한다. 통합 전 상품 ID로 진입해도 대표 상품의 현재 코드 그룹을 찾는다. 삭제된 주문은 그룹·매입 내역·그룹 이력에서 제외하며 마지막 주문을 삭제하면 상품 행도 사라진다. 삭제된 주문의 전체 이력 및 개별 조회는 기존 경로에서 보존한다. 소진 후 삭제된 상품은 남은 주문으로 상품 재고를 조회할 수 있다. 상품 페이지의 기존 상품 ID별 합계는 유지하며 재고 화면 진입 시 코드 그룹 전체를 표시한다. 상품코드별 집계에는 새 테이블이나 구매 데이터 변환을 사용하지 않는다.

## 참조·권한

- `inventory_purchase` → `inventory_item` → `inventory_movement`; 항목은 `catalog_product.id`를 필수 참조하고 `product_supplier.id`는 선택 참조한다. 등록 시 판매글이 선택 상품에 속하는지 확인한다.
- `origin_product_id`, 구매 옵션과 매입 건은 상품 수정·통합과 별개로 보존한다. 현재 연결 상품 정보는 주문·상품·이력 조회에 공통 적용한다. 통합하면 현재 `product_id`만 대표 상품으로 옮기고 항목 버전을 증가시킨다.
- 보유 또는 미입고 수량이 있는 상품은 삭제할 수 없다. 소진 후 삭제한 상품도 재고 화면에서 삭제된 상품의 현재 정보와 이력을 조회한다. 삭제 상품에 수량을 다시 늘리는 작업은 거절한다.
- ADMIN: 구매·결제·단가·환불을 포함한 전체 관리. PRODUCT: 보유·미입고·옵션·상품 메모, 입고와 허용된 기록 취소. 기존 입출고 API 권한은 유지한다. VIEWER: 접근 불가.
- PRODUCT 응답에는 단가·잔여 금액·매입 합계·기존 결제 금액·주문번호·주문서 URL·결제 정보·비공개 메모·환불 정보가 포함되지 않는다. 비공개 항목을 화면에서만 숨기는 방식이 아니다. 구매 주문 검색도 관리자가 아니면 주문번호를 검색하지 않는다.

## API

모든 API는 기존 `ApiResponse`, 목록은 `PageResponse`를 사용한다. ID는 문자열이다. 페이지는 0부터, 크기는 20/50/100이다.

| API | 동작 |
|---|---|
| GET `/api/inventory/stock-products?q&productId&brandId&page&size` | 상품코드별 재고 그룹 목록; 기본 크기 100 |
| GET `/api/inventory/stock-totals?q&productId&brandId` | 전체 보유 수량과 검색 결과 보유 수량(페이지와 무관한 정수 문자열) |
| GET `/api/inventory/stock-products/{productId}` | 그룹 대표 상품·합계·옵션별 수량 |
| GET `/api/inventory/items?q&productId&groupProductId&state&page&size` | 매입일 순 매입 항목 목록; 상태 ALL/ON_HAND/PENDING/EMPTY |
| GET `/api/inventory/items/{id}` | 현재 상품 정보와 주문·입고·미입고·취소·실제 보유 수량 |
| GET `/api/inventory/summaries?productIds=id1,id2` | 최대 100개 상품의 보유·미입고 합계를 묶음 조회 |
| GET `/api/inventory/purchases?q&brandId&page&size` | 구매 주문 목록 |
| GET `/api/inventory/purchases/{id}` | 주문과 소속 재고 항목 |
| POST `/api/inventory/purchases` | 미입고 상태의 주문 등록 |
| POST `/api/inventory/purchases/{id}` | `revision`을 검사해 주문 메타데이터 수정 |
| POST `/api/inventory/purchases/{id}/delete` | ADMIN 전용, 주문·항목·환불 상태 확인 후 미입고 취소 및 주문 삭제 |
| POST `/api/inventory/items/{id}` | `revision`을 검사해 구매 항목/운영 정보 수정 |
| POST `/api/inventory/items/{id}/movements` | 입출고·실사 정정·기록 취소 |
| GET `/api/inventory/movements?itemId&productId&groupProductId&brandId&page&size` | 발생 일시·담당자·원기록·취소 상태를 포함한 이력 |
| POST `/api/inventory/movements/{id}/refund` | 환불 버전을 검사해 매입 반품의 환불 정보 수정 |

`groupProductId`는 선택적이며 서버가 해당 상품의 현재 코드 그룹을 찾는다. 기존 `productId`·`itemId` 필터는 기존 의미를 유지하며 필터를 함께 주면 교집합이다. 그룹 필터의 매입 항목·이력은 활성 주문만 포함한다.

요청 DTO는 `InventoryDtos`에 정의한다. 수량·원화 금액·버전은 JSON 정수만 받으며 소수점 값을 자동 절삭하지 않는다. 주문 생성·수량 기록에는 UUID `X-Operation-Id`가 필수다. 동일 UUID와 동일 내용은 결과를 재조회하고, 다른 내용은 409로 거절한다. 브라우저는 같은 입력으로 재시도할 때 UUID를 유지한다. 버전 충돌은 다시 조회 후 입력 내용을 확인해야 한다.

V26은 `inventory_item.location` 컬럼과 기존 위치 값을 제거한다. 과거 요청의 `location` 필드는 호환성을 위해 받아들이지만 저장하거나 응답하지 않는다. 주문 생성·입출고의 기존 요청 해시 계산은 유지하여 과거 UUID/내용 재시도가 한 번만 반영되도록 한다.

## 결제 수단 설정과 업그레이드

V23은 결제 수단 테이블과 주문의 `paymentMethodId`, `paymentAmount`를 추가한다. 기존 V22 구매·입고·반품 이력과 자유 입력 결제 정보는 보존하며 기존 결제 금액은 null이다. 기본 수단은 카드·계좌이체·현금이다. 관리자만 공통 설정의 결제 수단 탭 및 `/api/settings/payment-methods`에 접근한다. GET 목록, POST 추가, POST `/{id}` 이름 수정, POST `/{id}/delete` 삭제를 제공하며 수정·삭제는 버전을 검사한다.

삭제는 비활성 처리하고 주문 참조를 보존한다. 주문은 선택 당시 표시명을 저장하며 수단 이름 변경/삭제 이후에도 이전 표시명을 유지한다. 삭제된 기존 선택은 해당 주문 수정 시 유지할 수 있지만 새 주문에는 선택할 수 없다. PRODUCT 응답에서 결제 금액·수단 ID도 제거한다. 상품의 공개 메모는 ‘상품 메모’, 주문 비공개 메모는 ‘결제 메모’로 표시한다. 기존 카드·계좌 별칭은 이력에 보존한다.

공통 알림 버튼은 사이드바에서 제공하며 모바일에서는 메뉴를 열어 접근한다. 우측 고정 아이콘을 표시하지 않는다.

쓰기 작업은 기존 공통 상품 잠금을 먼저 얻고 해당 재고 행을 잠근다. 상품 통합·삭제와 입출고를 동일 순서로 직렬화한다. 수량과 이력을 같은 트랜잭션으로 확정하고 DB CHECK로 범위를 보호한다. 현재 수량은 항목의 집계값이며 입출고 원장을 보존한다. CSRF·최신 계정 검사와 작업 감사도 적용한다. 주문서 URL은 HTTP/HTTPS 링크로만 저장·표시하며 서버가 내용을 가져오지 않는다.

V25는 `inventory_item.purchased_code`, `purchased_name`과 기존 값을 제거한다. 이전 마이그레이션은 수정하지 않는다. 상품 참조·수량·단가·옵션·이력은 유지하며 과거 요청의 해당 DTO 필드는 기존 요청 해시 검증에만 사용한다. 과거 저장된 요청의 해시를 바꾸지 않아 같은 UUID/내용의 생성 재시도가 유지된다. 상품코드 변경·통합 이후 주문과 이력도 현재 연결 상품의 정보를 표시한다.

## 구매 주문 삭제

주문 상세 우측 하단의 관리자 전용 삭제 버튼은 보유 수량이 0이고 환불 대기 기록이 없을 때만 사용할 수 있다. 삭제 확인창에 해당 주문과 취소할 미입고 총수량을 표시한다. 보유 재고는 삭제로 강제 차감하지 않는다. 관련 입출고를 먼저 정리해야 한다.

V24는 주문에 삭제 일시·담당자·요청 식별자를 추가하며 기존 데이터의 삭제 상태는 null로 유지한다. 삭제 시 남은 미입고 수량마다 `CANCEL_PENDING` 기록(사유: 구매 주문 삭제로 미입고 취소)을 추가한 후 주문을 비활성화한다. 취소와 삭제는 같은 트랜잭션에서 확정한다. 구매 주문·재고 목록과 상품 합계에서는 제외하고 상품 참조·구매 옵션·결제 및 완료된 환불·기존 입출고 이력은 보존한다. 이력에서는 삭제된 주문임을 표시하며 항목 조회는 가능하지만 수정·새 이동·기록 취소·환불 변경은 거절한다. 복원 기능은 제공하지 않는다.

삭제는 `revision`, 관리자 상세 조회의 `deleteToken`, UUID `X-Operation-Id`를 받는다. `deleteToken`은 항목 버전(상품 통합 포함)과 모든 입출고·환불 버전을 함께 검사한다. 확인 후 변경된 주문은 409로 거절하고 최신 상태로 재확인한다. 동일 요청 재시도는 미입고 취소를 반복하지 않는다. 삭제 권한, CSRF, 최신 계정 검사와 `INVENTORY_PURCHASE_DELETE` 감사 기록을 적용하며 삭제 확인 정보는 PRODUCT 응답에서 제거한다.

## 적용·검증

V22는 기존 V1~V21을 수정하지 않고 빈 재고 테이블 세 개를 추가한다. 기존 상품·선정·조회 이력과 외부 재고 수량은 그대로 보존한다. 정상 배포 절차에 따라 DB를 백업하고 새 애플리케이션을 시작하면 Flyway가 적용한다. 초기 보유 물건은 매입 주문과 초기 입고로 등록한다. 운영 DB에서 테스트하지 않는다.

```sh
JAVA_HOME=/path/to/jdk21 bash scripts/test-integration.sh \
  -Dtest=InventoryFlowIT,ProductFlowIT,MigrationUpgradeIT,LayoutViewTest \
  -DargLine=-javaagent:/path/to/mockito-core.jar
node --test src/test/js/*.test.cjs
NODE_PATH=/path/to/node_modules node scripts/test-inventory-ui.cjs
NODE_PATH=/path/to/node_modules node scripts/test-product-ui.cjs
```

통합 검증은 임시 MySQL·Redis만 사용한다. Maven 의존성 캐시가 없을 때 `MOLEBUTTER_TEST_MAVEN_OFFLINE=false`로 다운로드를 허용할 수 있다. 브라우저 검증은 실제 Thymeleaf 렌더링과 모의 API를 사용하며 `target/ui-check/`에 화면을 저장한다. 판매 예약·판매채널 연동·다중 장소 이동·복수 결제·원가 배분은 이번 버전에 포함하지 않는다.
