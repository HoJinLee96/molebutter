# 검색어 기반 매입처 가격·재고 조회

상품은 판매 플랫폼과 독립적으로 등록합니다. 전체 상품코드가 등록 기준이며, 네이버 검색과 매입처의 실제 옵션 조회를 한 번의 최신화 작업으로 실행합니다. 판매가 계산·판매채널·판매용 파일 생성은 제공하지 않습니다.

## 사용 순서

1. 공통 설정에 브랜드를 등록합니다. 닥스·헤지스·질스튜어트는 브랜드 ID에 잡화 규칙을 연결하며 이름을 바꾸어도 연결을 유지합니다.
2. 상품 화면에서 직접 등록하거나 기존 XLSX를 일괄등록합니다. 등록·수정 항목은 브랜드 / 전체 상품코드 / 네이버 검색어입니다. 브랜드는 등록된 항목과 미지정만 선택합니다. 수동 등록의 상품코드·검색어는 필수이며 검색어 초기값은 비어 있습니다.
3. **공통 설정 → 선호 매입처**에서 쇼핑몰 전체 또는 특정 매장을 등록합니다. 선호 목록이 비어 있으면 예약·선택 최신화를 시작하지 않습니다.
4. 상품의 **매입처 비교 → 최신화**를 누릅니다. 별도의 링크·구매 옵션 연결은 필요 없습니다. 진행 중에는 로딩을 표시하고 2.5초 간격으로 가벼운 상태 API만 확인합니다. 완료되면 상세와 목록을 한 번 다시 조회해 페이지 새로고침 없이 결과를 표시합니다. 기본 정보의 저장 전 입력은 유지하며, 모달을 닫으면 상태 확인을 중단합니다. 일시적인 연결 오류는 재확인하고 중단·접속 제한은 완료와 구분해 안내합니다.
5. 큰 상품 사진·쇼핑몰·지점·네이버 검색 가격과 배송비·옵션별 구매 가능 여부·재고 수량을 확인합니다. 상품 링크와 매입처 원문 모델 코드(있는 경우)를 함께 표시합니다. 코드·브랜드·시즌·색상 일치 여부는 자동 판정하지 않습니다.
6. 매장별 묶음에서 **매입처로 선정**합니다. 묶음은 모달을 열면 접혀 있고, 재고를 확인한 판매글과 선정한 판매글은 항상 맨 위에 보이며 나머지는 '펼치기'로 확인합니다. 하나의 판매글만 선정하며 더 저렴한 글이 나와도 자동 변경하지 않습니다. 가격은 네이버 가격을 사입 기준가로 사용하고 배송비는 별도로 표시합니다. 재고 확인과 선정은 별개입니다.

상품 메뉴 진입 시 전체 조회, 검색 조건 초기화, 기본 100개를 적용합니다. 20·50·100개, 숫자 페이지, 처음·마지막 이동을 지원합니다. 자동관리 해제는 예약·전체 실행에만 영향을 주며 선택 최신화는 가능합니다. 실행 중인 상품은 완료·취소 후 삭제/통합할 수 있습니다. 삭제는 목록 제외 방식이며 이력은 남습니다.

상품 최신화 화면의 작업 이력은 기본으로 최근 7일(한국 시간, 오늘 포함)을 20개씩 보여 줍니다. 시작일·종료일, 작업 상태, **실패 있는 작업만**(실패 재조회 대상 상품이 남은 작업)으로 조회하고 20·50·100개와 숫자 페이지를 지원합니다. 날짜를 비우면 그쪽 경계 없이 조회합니다. 조건은 새로고침하면 기본값으로 돌아가며 URL에는 선택한 작업(`?run=`)만 남깁니다. 진행 중·중단·자동 재개 대기·접속 제한 작업이 현재 조회 결과에 없으면 목록 위 **진행 중인 작업**에 따로 표시해 언제든 제어할 수 있습니다. 재조회 대상이 없는 작업의 실패 재조회 버튼은 비활성화합니다. 작업·상품 이력은 삭제하지 않고 계속 보관합니다.

## 검색어와 기존 데이터

저장된 네이버 검색어로 판매글을 찾고 실제 매입처·선호 조건·가격·재고만 판별합니다. 다른 코드나 브랜드, 코드가 없는 결과도 포함될 수 있으므로 사용자가 사진과 상품 페이지로 확인합니다. 쇼핑몰 API의 요청·응답 상품 ID 검사는 유지합니다. 새 결과의 상태는 `SEARCH_RESULT`이며 코드 일치를 의미하지 않습니다.

브랜드·상품코드 변경, 일괄 브랜드 지정·자동 판단은 저장된 검색어를 덮어쓰지 않습니다. 신규 엑셀 상품만 브랜드를 판별한 뒤 기존 잡화 규칙으로 초기 검색어를 만듭니다. 닥스·헤지스·질스튜어트에서 `ABCD6F123BK`는 `ABCD123`, 그 밖의 형식은 전체 상품코드를 사용합니다. 재등록 상품의 검색어는 유지합니다.

`codeType`·`searchMode` 요청은 호환용이며 검색어 생성에 사용하지 않습니다. 기존 응답 필드와 DB 컬럼은 유지합니다. 과거 `MATCHED` 결과는 기존 판정으로 읽으며 `REVIEW`·`EXCLUDED` 결과를 소급해서 정상 판정하지 않습니다.

새 작업의 `selection_snapshot`에는 `lookupPolicy: "SEARCH_QUERY"`를 저장합니다. 누락·null인 이전 작업은 취소 후 새로 실행해야 합니다. 기존 결과·선정·이력은 변경하지 않으며 새 마이그레이션은 없습니다.

## 가격·재고와 조회 상태

- 목록과 상세 상단의 가격은 **선정한 판매글의 네이버 가격(사입 기준가)**입니다. 미선정 상품에 최저가를 대신 표시하지 않습니다. 배송비는 별도이며 품절·재고 미확인 판매글도 선정할 수 있습니다.
- 상품 대표 사진(목록·비교 상단)은 선정한 판매글의 최신 사진입니다. 선정이 없거나 그 판매글에 사진이 없으면 마지막 최신화에서 첫 판매글(검색 1순위) 사진을 씁니다. 비선호 추천 판매글 사진은 대표로 쓰지 않으며, 작업이 중단·대기 중인 동안에는 최신화 사진이 갱신되지 않습니다.
- 같은 쇼핑몰·확인된 매장의 판매글은 묶어 표시합니다. 묶음과 묶음 안 판매글 모두 선정 여부와 관계없이 가격이 낮은 순입니다. 이번 조회 가격이 없으면(대기·중단·취소 등) 마지막으로 확인한 가격 기준이며, 가격이 전혀 없으면 맨 뒤입니다. 개별 사진·코드·재고·바로가기는 보존하며 재고를 합산하지 않습니다.
- 실제 매장·채널이 미확인인 결과는 비교 영역에 표시하지 않고 최신화 결과에 미확인 건수를 표시합니다. 수동 지정은 해당 판매글에만 저장합니다. 이후 자동 판별이 달라도 수동 지정을 덮어쓰지 않고 원문과 차이를 표시합니다. 스마트스토어는 검증된 상품 URL의 실제 판매자 경로가 있을 때만 판매자를 구별합니다.
- 가격은 확인되고 재고만 실패하면 새 기준가와 `재고 조회 실패`를 함께 표시합니다. 검색에서 빠지면 `이번 검색에서 미확인`이며 마지막 가격·시각은 참고용입니다. 선호 목록에서 제외해도 선정은 유지하고 제외 표시를 붙입니다.
- 새 옵션 결과에는 원문 옵션 ID·이름, 재고 수량, 구매 가능 상태만 저장합니다. 매입처 상품가·추가금·배송비·총 구매가는 조회·저장·화면에서 제외하고 네이버 검색 가격·배송비를 유지합니다. 기존 이력은 삭제하지 않으며 이전 가격 필드를 무시해서 읽습니다.
- 지점은 네이버 상품명, 해당 매입처 상품의 제목·매장 정보에서 확인된 표기와 근거를 저장합니다. 추천 상품 영역의 이름은 사용하지 않습니다. 없으면 `지점 미확인`, 서로 다른 지점이 나오면 `지점 확인 필요`로 표시합니다. 기존 결과의 지점 정보는 새 조회 후 채워집니다.
- 현재 상세 조회는 검증된 네이버 쇼핑윈도만 지원합니다. 일반 스마트스토어와 미확인·충돌 채널은 상세 조회·신규 선정·매장 수동 지정에서 제외하고, 기존 선정과 과거 확인값은 보존합니다. 현재 채널 판정과 호환 정책은 [네이버 채널 정책](naver-channel-policy.md)을 따릅니다.
- 구매 가능, 명확한 품절, 수량 미제공, 옵션 미확인, 조회 실패를 구별합니다. 대표 옵션 선택·재고 합산·매입처 사이의 옵션명 통합은 하지 않습니다.
- 네이버 검색 가격은 옵션별 확정 구매가로 환산하지 않습니다.
- 이전 정상 응답과 전체 조회 이력은 별도 참고 영역에 남습니다. 최신 조회가 실패하면 과거 가격을 현재 결과로 바꾸지 않습니다.
- 시작 시 선호 규칙과 매장 목록을 JSON으로 고정합니다. 비선호 쇼핑몰은 옵션 조회 전에 제외하고, 특정 지점이 확인되면 지점 규칙으로 거릅니다. 알려지지 않은 지점은 미확인으로 남깁니다. 선호 매입처를 찾았어도 검색 범위를 조기에 끝내지 않습니다.
- 동일 실행의 동일 검색어는 검색 결과를 공유하고 선호·선정 기준은 상품별로 적용합니다. 공유 검색 캐시에 비선호 쇼핑몰도 보존하여 다른 상품의 선정 확인·추천 후보로 사용할 수 있게 합니다. 새 매입처도 찾도록 최대 3페이지까지 보며 기존 링크 발견으로 조기 종료하지 않습니다.
- 작업은 DB에 저장하며 한 번에 하나만 실행합니다. 중단은 확인 중인 상품을 마친 뒤 멈춥니다. 취소는 다음 매입처 요청 전 확인하며 이미 진행한 HTTP 요청은 응답/시간 제한까지 걸릴 수 있습니다. 재시작 후 만료된 작업 임대를 회수해 미완료 항목을 재개합니다.
- 조회 기준의 `lookup_revision`과 표시·관리용 `revision`을 구분합니다. 실행 중 전체 상품코드·검색어가 바뀌면 이전 기준의 결과가 최신 결과를 덮어쓰지 않습니다. 브랜드·자동관리 변경만으로 조회 기준이나 가격을 변경하지 않습니다.

## 엑셀 일괄등록

현재 사용하던 XLSX만 읽습니다. `data` 시트 3행 헤더, 4행 이후 F열 전체 상품코드, H열 등록명(빈 값은 G열)을 사용합니다. 원본 파일·판매 옵션 ID·가격·승인상태·수정 요청 칸은 보존하거나 등록 기준으로 사용하지 않습니다. 등록명은 브랜드 판단용으로만 상품에 보존합니다.

같은 전체 코드의 반복 행은 한 대상으로 묶습니다. 다른 시즌의 코드는 별도로 등록합니다. 재등록은 기존 검색어·지정 브랜드·자동관리·매입처 정보를 유지하며 미지정 브랜드만 등록된 이름으로 판단합니다. 중복 행의 브랜드가 서로 다르거나 불분명하면 미지정으로 남깁니다. 기존 DB의 동일 코드가 여러 개면 임의 갱신하지 않고 통합 안내를 반환합니다.

결과는 전체 데이터 행 수, 신규·기존·중복·제외·브랜드 지정 건수와 행 번호별 안내입니다. 코드 없는 새 행은 제외합니다. 파일은 10MB/5,000행, 압축 해제 전체 100MB/항목 30MB/1,000항목 제한입니다. 매크로·외부 연결·DTD, 등록 셀 수식, 중복 행/셀 주소를 거부하고 실제 마지막 XML 행까지 읽습니다. 업로드 행위는 기존 감사 기록에 남습니다.

## 데이터와 API

| 책임 | 저장 구조 | API |
|---|---|---|
| 상품·브랜드·조회 기준 | catalog_product, procurement_product, product_brand | /api/products, /api/settings/brands |
| 등록 | 원본 미저장, 상품의 registration_names | POST /api/products/imports |
| 매입처 판매글·자동/수동 매장 지정·최근 관측 | product_supplier | 상품 상세 comparison, POST /api/products/{id}/suppliers/{supplier}/store |
| 매장·선호 규칙 | supplier_store, supplier_preference | /api/settings/supplier-stores, /api/settings/preferred-suppliers |
| 선정·변경 이력 | product_supplier_selection, product_supplier_change | POST /api/products/{id}/selection |
| 조회 당시 옵션·가격·재고 | product_lookup_history, procurement_product.latest_result | /api/products/{id}/history |
| 작업·상품 진행·검색 공유 | product_refresh_run, product_refresh_entry, product_refresh_search | /api/product-refresh |
| 작업 이력 조회 | product_refresh_run, product_refresh_entry | GET /api/product-refresh?from&to&status&failed&page&size&run → `items`·`page`·`totalPages`·`totalElements` + 조건과 무관한 `active`·`selected`·`stockLookupBlock` |
| 모달 진행 상태 | 현재 조회 기준에 해당하는 작업 상태만 읽음 | /api/products/{id}/refresh-status |
| 예약·작업 임대 | procurement_settings, procurement_runtime | /api/product-refresh/settings |

ID는 문자열로 반환합니다. 목록과 작업 결과에는 선정 가격·재고 요약을 반환하며 비교와 전체 이력은 상세에서 제공합니다. ADMIN·PRODUCT는 상품 업무를 사용할 수 있으며 설정 변경은 ADMIN만 허용합니다. 민감 조회의 최신 계정 검사, 변경 요청의 CSRF·감사·버전 충돌 검사를 유지합니다.

## V12 적용

`V12__preferred_suppliers.sql`은 매장·선호 규칙·선정과 변경 이력을 추가합니다. V1~V11 파일은 수정하지 않았습니다. 기존 상품·판매글 ID와 조회 이력을 보존하고, 최근 결과를 기존 판매글에 연결합니다. 모든 상품의 선정과 공통 선호 목록은 빈 상태로 시작합니다.

- 서버 재시작으로 V12 적용 후 관리자가 선호 매입처를 먼저 등록합니다. 기존 지점이 미확인인 판매글은 새로 조회하거나 수동 지정합니다.
- V11에서 시작해 선호 스냅샷이 없는 작업은 외부 조회를 하지 않고 중단 안내를 표시합니다. 해당 작업을 취소하고 선호 설정 후 다시 실행합니다.
- 상품 통합 때 여러 선정이 있으면 유지할 판매글을 명시해야 합니다. 같은 판매글의 중복 행은 기존 ID를 삭제하지 않고 대표 행을 연결해 보관합니다.
- 조회 결과 저장은 선정·수동 지정 컬럼을 덮어쓰지 않습니다. 사용자 변경은 공통 잠금과 상품/판매글 버전으로 충돌을 검사합니다.
- V11 → V12 기존 데이터 전환과 빈 DB 전체 마이그레이션은 임시 MySQL에서 검증합니다. 실제 프로젝트 DB에는 테스트 데이터를 쓰지 않습니다.

## V11 적용 절차

실제 프로젝트 DB에는 개발 테스트로 마이그레이션하지 않았습니다. 서버를 새 버전으로 시작하면 Flyway가 적용합니다. 기존 V1~V10은 수정하지 않습니다.

1. **이전 버전에서** RUNNING·PAUSED·BLOCKED 최신화를 완료하거나 취소합니다. 새 버전은 이 상태가 남아 있으면 DDL 전에 시작을 막습니다.
2. 이전 서버를 종료해 쓰기 작업을 멈추고 DB 전체를 백업합니다. 예를 들어 이미 설정한 MySQL login-path로 다음 명령을 실행합니다. 비밀번호를 명령문이나 Git에 넣지 않습니다.

   ```sh
   mysqldump --login-path=molebutter-backup --single-transaction --routines --triggers --hex-blob --no-tablespaces --set-gtid-purged=OFF molebutter > molebutter-before-v11.sql
   ```

3. 백업 파일 생성 성공과 복구 가능 여부를 확인하고 새 서버를 시작합니다.
4. V11이 기존 상품 ID·브랜드·관리 상태를 보존하고 매입처 URL/ID 및 옵션 조회 이력을 옮깁니다. 상품에 연결되지 않았던 등록 항목도 각각 보존하고 같은 코드라고 자동 합치지 않습니다. 기존 가격은 참고 이력이며 새 가격은 다시 조회합니다.
5. 상품·매입처·조회 이력 수를 대조한 후 원본 파일·판매·계산·구매 옵션용 테이블을 제거합니다. 기존 예약 설정은 그대로 둡니다. 코드 누락 상품은 보완 대상으로 남습니다.
6. 상품 수, 미지정 브랜드, 수동 검색어와 이전 이력을 확인하고 한 상품을 선택 최신화합니다.

MySQL DDL은 실패 시 자동 롤백되지 않습니다. DDL 시작 후 실패했다면 원인을 확인하고 백업 복구 후 재시도해야 합니다. 운영 DB에서 `flyway_schema_history`만 삭제하거나 확인 없이 repair하지 않습니다. 롤백할 때는 **이전 애플리케이션과 V10 백업을 함께** 복구합니다.

## 검색 브라우저 준비

서버에 Chrome과 화면을 표시할 수 있는 실행 환경이 필요합니다. 검색 요청 시 **실제 Chrome 창**을 띄우고 Playwright가 CDP로 연결합니다. 검색은 전용 스레드와 브라우저 한 개에서 직렬 실행합니다. 개인 Chrome 프로필을 복사하거나 연결하지 않고 브라우저 엔진 자동 다운로드도 끕니다.

```properties
# macOS 기본 경로. 다른 환경에서는 설치된 Chrome 실행 파일로 지정합니다.
product.search.chrome-executable=/Applications/Google Chrome.app/Contents/MacOS/Google Chrome
product.search.delay-ms=3000
product.search.ui-stabilization-ms=2000
product.refresh.worker-enabled=true
```

Chrome 실행 옵션은 at-a-glance와 같이 **0이 아닌 CDP 포트**를 전달합니다. 9223을 공유하지 않고, 사용 가능한 로컬 포트 번호를 먼저 정해 기존 프로젝트와의 충돌을 피합니다. `--remote-debugging-port=0`은 Chrome의 `navigator.webdriver` 상태에도 영향을 주므로 사용하지 않습니다. 사용자 에이전트나 브라우저 속성을 덮어쓰는 스크립트는 넣지 않습니다. [MDN 설명](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/webdriver)

로그인 주소 차단은 Chrome CDP의 URL 차단 기능으로 처리합니다. Playwright의 `route()`는 HTTP 캐시를 비활성화하므로 사용하지 않습니다. 검색용 일반 쿠키와 캐시, Chrome이 만든 요청 헤더는 유지하고 로그인 쿠키는 매 검색 과정에서 검사합니다. [Playwright 문서](https://playwright.dev/java/docs/api/class-browsercontext#browser-context-route)

전용 비로그인 프로필은 프로젝트의 `data/product-search-guest/`로 고정하며 Git에서 제외합니다. 이전 `data/product-search-browser/` 프로필은 사용하지 않습니다. 전용 프로필을 다른 서버가 사용 중이면 실행하지 않습니다. Chrome 잠금 파일은 존재 여부만으로 실행 중이라고 판단하지 않고 소유 컴퓨터와 프로세스 생존 여부를 검사합니다. 같은 컴퓨터에서 이미 종료된 프로세스의 Singleton 잠금 링크만 정리하며, 실제 실행 중인 프로세스·다른 컴퓨터·소유자 불명 잠금은 유지합니다. 서버 종료 시에는 작업 중단 신호와 별개로 Chrome의 정상 종료를 기다립니다. 개인 프로필 경로나 headless 설정은 받지 않습니다.

기존 at-a-glance의 `NaverChromeWorkerLauncher`와 `NaverShoppingBrowserSearchClient`에서 다음 흐름을 가져왔습니다.

1. 네이버 홈에서 검색어를 입력하고 통합검색으로 이동합니다.
2. **가격비교 더보기** 링크를 실제로 클릭합니다. 해당 링크가 없으면 **상단 쇼핑 탭**을 클릭합니다. 새 탭이 열리는 경우에도 가격비교 탭을 이어 사용하며 검색어가 같은지 검사합니다.
3. **낮은 가격순**을 클릭하고, 가격 적용기준이 켜져 있으면 **OFF**로 바꿉니다. 처음 40개로 조회한 뒤 전체 건수가 40개보다 많으면 80개씩 보기로 변경합니다.
4. 화면 클릭으로 발생한 검색 응답만 읽습니다. 요청과 응답 양쪽에서 검색어·정렬·페이지·표시 개수를 대조하고, 적용기준 OFF가 확인된 응답만 최종 가격으로 사용합니다. 추가 페이지도 화면의 버튼을 클릭하며 최대 3페이지까지 확인합니다.

**가격 검색 중에는 로그인하지 않습니다.** 네이버 인증 주소로 가는 요청을 차단하고, 로그인 쿠키가 발견되면 검색을 중단합니다. 로그인 화면이나 보안 확인 화면이 나타나도 로그인을 안내하거나 자동으로 통과시키지 않습니다. 실제 제한은 잠시 후 사용자가 재조회해야 하며, 검색 경로 개선이 네이버의 접속 허용을 보장하지는 않습니다.


## V13 매장 판별과 외부 식별자

더현대Hi·롯데ON·네이버 매장 정보를 상품 ID에 한정해 읽습니다. 더현대Hi는 `storeNm/storeCd`, 롯데ON은 상품·판매자의 `lrtrNm/trNm/trGrpNm`, 네이버는 `channel.storeCategory.wholeNames/wholeIds`를 사용합니다. 롯데 판매자 코드는 판별 근거에 보관하며 지점 공통 식별자로 단정하지 않습니다. 추천 상품이나 다른 상품 ID의 정보는 사용하지 않습니다.

네이버는 매장 정보만 조회하고 옵션·재고는 계속 미확인으로 남깁니다. 검색 전용 비로그인 Chrome에서 얻은 공개 User-Agent와 한국어 Accept-Language를 HTTP 요청에 사용하며 쿠키·인증 정보는 전달하지 않습니다. 아직 검색 브라우저를 사용하지 않은 프로세스에서는 버전이 없는 `Mozilla/5.0`을 사용합니다. 204는 정보 미제공, 302는 조회 실패로 구분하고 자동 리다이렉트하지 않습니다. 접속 제한은 기존처럼 작업을 중단합니다. 실행 중 동일한 매입처 상품의 성공한 상세 응답은 메모리에 재사용하며 다른 실행으로 넘어가면 비웁니다. 프로세스 재시작 후에는 다시 조회합니다.

`V13__supplier_store_identity.sql`은 기존 내부 매장 ID를 유지하고 백화점명 및 외부 식별자 연결을 추가합니다. 외부 식별자로 확인된 매장은 표시명이 바뀌어도 같은 매장입니다. 같은 이름의 다른 백화점 지점은 합치지 않으며, 같은 외부 식별자가 다른 백화점·매장 종류를 가리키면 충돌로 남깁니다.

- 더현대Hi의 기존 매장은 지점명·별칭이 유일하게 일치하면 연결합니다.
- 여러 백화점이 있는 플랫폼의 기존 매장은 백화점 구분도 확인합니다. 이름만 있는 모호한 매장은 확인 대기에 보관합니다.
- 공통 설정에서 백화점명을 보완하거나, **확인된 지점과 기존 매장 연결**에서 관리자가 같은 매장임을 확인해 연결할 수 있습니다. 연결은 다음 조회부터 적용합니다.
- 수동 지정과 상품별 선정은 유지합니다. 이번에 지점을 확인하지 못한 기존 매장은 `이전 매장 정보 · 이번 지점 미확인`으로 표시하고 자동 확인 결과로 사용하지 않습니다.
- 최신화 중에는 앞서 확인한 매장을 선택할 수 있으며, 작업 완료가 그 선정을 덮어쓰지 않습니다.

설정 API에 `GET /api/settings/supplier-store-identities`, `POST /api/settings/supplier-stores/{id}/identity`를 추가했습니다. 연결 요청에는 매장 버전, 확인한 판매글 ID, 관측 실행 ID가 필요하며 관리자·최신 계정·CSRF·충돌 검사를 적용합니다. 기존 결과 JSON과 작업 스냅샷은 새 선택 필드가 없어도 읽습니다.

배포 전 진행 작업은 완료하거나 취소합니다. 서버 재시작 시 V13이 적용되며, 소수 상품을 선택 최신화해 매장 판별을 먼저 확인합니다. 자동 재조회나 매입처 자동 선정은 하지 않습니다.

2026-09-26 적용 검증: 별도 임시 MySQL의 빈 DB/V12 전환, 기존 선정·수동 지정·가격 보존, HTTP 204/302/429, 상품 ID 불일치, 추천 상품 오탐, 백화점 충돌, QHD/모바일 설정을 검증했습니다. 수정된 실제 Java HTTP 코드로 더현대Hi 신촌점·롯데ON 잠실점·네이버 현대백화점 천호점을 비로그인 조회했습니다(`target/v13-live-results.json`). 이는 소수 샘플 결과이며 모든 스마트스토어·상품 유형의 지원을 의미하지 않습니다.

### 스마트스토어 공식 브랜드몰 등록 (2026-09-27)

스마트스토어 특정 매장 선택창은 `백화점 지점 추가`와 `공식몰 추가`를 제공합니다. 공식몰은 관리자만 상품 링크로 판매채널을 확인하고 등록합니다. 확인 단계는 저장하지 않으며, 등록한 매장은 목록에서 따로 선택해 선호 설정을 저장합니다. 닥스·헤지스 외 채널도 등록할 수 있고 공식 여부는 관리자가 판단합니다.

- `POST /api/settings/supplier-stores/channel-preview`: `productUrl`로 본상품 판매채널 이름·UID와 설정 버전을 확인합니다.
- 기존 매장 생성 API에 `kind=BRAND_STORE`, `productUrl`, `expectedChannelUid`, `preferenceRevision`, 표시 `name`을 보냅니다. 서버가 다시 확인한 채널만 저장합니다. 홈페이지·임의 호스트·상품 ID 없는 링크는 거절하며 입력 URL을 직접 요청하지 않습니다.
- 기존 `NAVER_CHANNEL + channelUid`의 SELLER를 같은 ID의 BRAND_STORE로 전환합니다. 다른 채널과 이름으로 합치지 않으며, 이미 등록한 공식몰은 재사용합니다. 등록/전환/식별자 연결과 설정 버전 변경은 한 트랜잭션입니다. 새 마이그레이션은 없습니다.
- 상품 담당자는 기존 공식몰을 판매글에 지정할 수 있습니다. 현재 채널 근거가 없거나 다른 채널이면 공식몰 지정·선정을 허용하지 않습니다. 기존 선정은 해제하지 않습니다.
- 작업 시작 시 선호 스냅샷과 기존 지점 구분 정책을 유지합니다. 공식몰 등록은 스마트스토어 재고 조회를 활성화하지 않습니다.

### 스마트스토어 옵션·재고 활성화 (2026-09-27 후속 변경)

앞선 매장 정보 전용/DEFERRED 정책을 새 조회부터 해제했습니다. 기존 `/v2/channel-products/{채널상품번호}` 응답 하나에서 매장과 옵션 정보를 함께 읽으며 추가 API나 캐시는 만들지 않습니다. 과거 저장된 보류 결과는 수정하지 않으므로 상품 최신화가 필요합니다.

- 루트/본문 상품 ID를 검증하고 `contents.optionCombinations`의 실제 조합 ID·이름·수량을 읽습니다. 기존 루트/`optionInfo` 형식도 유지합니다. 중복 ID 충돌·누락된 옵션은 전체 확인으로 처리하지 않습니다.
- `optionUsable=false`가 명시된 경우에만 상품 수량을 단일상품 재고로 사용합니다. 상품 전체 재고를 개별 옵션에 나누거나 복사하지 않습니다.
- 누락·음수·소수·숫자가 아닌 값·외부 재고는 수량 미확인입니다. 명시적 0, 판매 중단/옵션 비활성, 통신 실패는 구분합니다. 상품 상태를 확인하지 못하면 양수 수량만으로 구매 가능이라고 표시하지 않습니다.
- 본상품 모델 코드의 `contents.naverShoppingSearchInfo.modelName`을 사용합니다. 선호 채널/지점 판단·조회별 캐시·접속 제한 중단은 유지합니다.
- 정상 비교 영역의 자동 확인 판매글에는 매장 지정 변경을 표시하지 않습니다. 확인 대기에는 지정 기능을, 기존 수동 지정에는 해제 기능을 유지합니다. 수동 지정과 자동 판별이 충돌하는 경우에는 수정할 수 있습니다. 네이버 표시명과 매장명이 같으면 한 번만 표시합니다.

`NaverInventoryTest`는 연구 응답 3건과 품절·판매불가·수량 미확인·ID 불일치·일부 옵션을 검증합니다. 수동 외부 실조회 테스트는 제거하고 저장된 응답으로 회귀를 검증합니다. 이번 실제 검증 시 백화점 단일상품 41개, 헤지스 FREE 3개, 닥스 FREE 2개를 확인했습니다. 이 수량은 검증 당시 값이며 구매 시점의 재고를 보장하지 않습니다.

## 선호 매입처와 비선호 추천 (V16)

- 비교 화면은 확인된 선호 매입처와 비선호 추천을 구분한다. 과거 확인 대기/제외 결과는 조회 이력에 보존하며 `pending`, `excluded` 응답은 빈 배열이다.
- 작업 생성 시 각 entry에 선정 판매글 ID, 검색 키, 선정 시각, 마지막 선정 변경 ID를 저장한다. 같은 시각에 변경하거나 같은 글을 재선정해도 기존 추천을 재사용하지 않는다.
- 선정 판매글의 이번 검색 상품가에서 1,000원 이상 낮은 비선호 글만 추천한다. 배송비는 별도다. 선정 가격 미확인 시 추천을 보류한다.
- 일반 판매자는 추천하지 않는다. 스마트스토어는 확인된 백화점 지점/등록 공식몰, 롯데ON은 백화점 지점/주식회사 LF만 대상이다. 완전히 확인된 모든 옵션이 판매 불가인 경우 제외하며 부분 확인·수량 미제공·재고 조회 실패는 별도 표시한다.
- 선정 → 선호 → 비선호 후보 순으로 조회한다. 기존 실행별 상세 캐시를 재사용하며 추천 추가 요청은 상품당 40건이다. 가격순으로 확인하고 상한에 도달하면 일부 조회를 표시한다.
- 선정 API는 현재 비교 결과의 선호 글 또는 유효 추천을 재검사한다. 추천 선정은 공통 선호를 변경하지 않으며 비선호 선정 글도 이후 최신화에서 계속 확인한다.
- 추천에서 선정한 비선호 판매글(또는 선정 뒤 선호에서 빠진 판매글)은 별도 '선정 매입처' 영역으로 옮기지 않고 비선호 추천 영역의 같은 매장 묶음에 그대로 두며, 선정 묶음은 파란 테두리로 표시한다.
- V16 적용 전 실행/중단 작업은 완료하거나 취소한다. 스냅샷 없는 과거 실행은 재개하지 않으며, 기존 선정/가격/이력에는 소급 변경이 없다. 서버 재시작 후 새 최신화부터 추천이 생성된다.
