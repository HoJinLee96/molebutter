# 네이버 검색 무응답 대기·재개 및 실패 진단 개선안

> 문서 유형: 과거 조사·설계·검증 기록. 수치·외부 응답·적용 여부는 기록 당시 기준이며 현재 실행 지침이 아니다. 개인 경로와 target 산출물도 당시 근거로 보존한다. 현재 정책과 실행 방법은 [문서 목차](README.md)에서 확인한다.

작성: 2026-09-29. 아래 확인 사실은 구현 전 조사 기준이다. 승인 후 V21·검색 복구 서비스·진단 API·화면을 구현하고 격리 환경에서 검증했다. 운영 서버 재시작과 운영 DB 마이그레이션은 수행하지 않았다. 적용 방법은 `naver-search-retry.md`를 따른다.

현재 재조회 대상은 SUCCESS·SOLD_OUT·과거 NO_MATCH·PENDING·CHECKING을 제외한다. 아래 운영 건수와 재조회 대상 제안은 구현 전 조사 기록이다. 현재 정책은 [검색 재시도](naver-search-retry.md)와 [검색 완료 판정](search-completion-status.md)을 따른다.

## 1. 확인 사실과 불확실한 부분

- `NaverBrowserNetwork.install`은 로그인 주소의 최상위 navigation만 감지한다. 현재 검색 가격 API에서 시작된 백그라운드 로그인 redirect는 별도로 추적하지 않는다.
- `NaverPriceSearch.capture`는 요청과 일치한 응답만 수용한다. 요청 없음, 네트워크 실패, 본문 읽기 실패, 검증 불일치가 모두 마지막에는 30초 대기 실패로 합쳐질 수 있다.
- `SupplierRefreshWorker.process`는 일반 예외를 고정된 실패 문구로 저장한다. 이 경로에는 검색 시도별 단계·원인을 남기는 로그가 없다.
- 로그인만 5분 → 30분 → 1시간 → 2시간 → 수동 중단 정책의 대상이다. 일반 검색 실패는 FAILED로 확정하고 다음 상품으로 진행한다.
- 사용자 관찰상 정렬 무응답 이후 5분 휴식과 수동 테스트로 정상 복구됐다. 일시 장애에 대기·재개를 적용할 근거지만, 무응답 모두가 로그인 또는 제한이라는 증거는 아니다.
- 첨부 대화의 56건 원인·45건 복구·시간대 집계는 전달받은 분석이다. 원본 네트워크/콘솔 자료를 재검증하지 않았으므로 과거 전체 원인을 로그인 redirect로 확정하지 않는다. HTTP 200·과거 성공만으로 제한이나 응답 불일치를 배제할 수도 없다.
- 운영 DB 읽기 전용 확인: 작업 `892380783276764856`은 2026-09-28 21:02:38 시작, 2026-09-29 01:08:59 완료. 총 284상품 중 SUCCESS 210, SOLD_OUT 1, FAILED 56, PARTIAL 12, NO_MATCH 5다. 재조회 대상 73 = 56 + 12 + 5이며 삭제·통합으로 제외되는 항목은 없었다.
- FAILED 56건 모두 동일 작업·검색어의 검색 캐시가 없다. 정상 검색 결과 저장 이전 단계의 실패와 일치하지만, 세부 원인은 이 자료만으로 확정하지 않는다. 작업의 로그인 감지 횟수는 0이며, 이는 현행 감지기에 기록되지 않았다는 뜻이다.
- 롯데홈쇼핑 추천: 21:06:08 HTTP 403 실패 1건 이후 추천 판매글 54건(41상품)을 생략했다. 이 숫자는 상품 재조회 73건과 직접 합산하지 않는다.
- PARTIAL 12상품에는 더현대Hi 김포점 OPTIONS_UNKNOWN 6판매글/5상품, Hmall OPTIONS_UNKNOWN 2판매글/2상품, 롯데ON OPTIONS_PARTIAL 본점 28판매글/5상품·영등포점 4판매글/2상품·지점값 없는 1판매글/1상품이 포함된다. 한 상품이 여러 행에 걸치므로 상품 수를 단순 합산하지 않는다. 모두 김포점 때문은 아니다.
- 확인 시 활성 작업(RUNNING/PAUSED/BLOCKED/RETRY_WAIT)은 없었다. 배포 직전에는 다시 확인한다.

## 2. 처리 정책

| 상황 | 처리 |
|---|---|
| 실제 로그인 화면/최상위 이동 | 기존 로그인 대기 정책 |
| 현재 검색 API에서 이어진 로그인 redirect 확인 | 같은 대기 정책, 원인은 API_LOGIN_REDIRECT로 별도 기록 |
| 정렬 클릭 후 검색 요청 없음 또는 응답 미완료·통신 실패 | SEARCH_NO_REQUEST / SEARCH_RESPONSE_TIMEOUT / SEARCH_NETWORK_ERROR로 대기 |
| 이번 검색의 응답이 왔지만 검색어·정렬·페이지 검증 불일치 | RESPONSE_MISMATCH로 기록. 휴식 후 한 번 재검증하고 동일 불일치 재현 시 수동 확인 중단 |
| 정상 응답 형식 오류·필수 화면 요소 누락 | RESPONSE_SCHEMA_CHANGED / UI_ELEMENT_MISSING. 일시 로딩 가능성 때문에 5분 후 한 번 재검증, 같은 문제 반복 시 수동 확인 중단 |
| HTTP 403·418·429, CAPTCHA·보안 확인 | 기존 수동 중단 유지. 일반 무응답 재시도로 바꾸지 않음 |
| 로그인 쿠키 발견·탭 정리 실패·브라우저 실행 불가 | 기존 수동 확인. 운영/환경 오류를 네이버 일시 무응답으로 분류하지 않음 |
| 취소·인터럽트·작업 소유권 상실 | 결과 반영·자동 재시도 즉시 중단 |
| 1~3페이지 정상 종료·정상 검색 결과 없음 | 성공. 페이지 제한 관련 기록·안내 생성 없음 |

분류는 타입/코드로 수행하고 예외 문구 문자열에 의존하지 않는다. 검색 전체 180초 제한은 실제 발생 단계와 진행 정보를 사용해 분류하며, 모든 시간 초과를 일괄 로그인으로 바꾸지 않는다. 검증 조건을 완화하여 잘못된 가격을 수용하지 않는다.

로그인/무응답의 권장 대기 간격은 기존 5·30·60·120분으로 통일한다. 다섯 번째 연속 감지 시 자동 재개를 중단한다. 로그인과 무응답이 번갈아도 성공 전에는 같은 연속 재시도 횟수를 이어 간다. 원인별 진단은 따로 보존한다. 정상 브라우저 검색 완료만 횟수를 초기화하며, 검색 캐시·쇼핑몰 재고 성공은 초기화하지 않는다.

## 3. 감지 경계

- 현재 검색 탭과 활성 검색 시도에 속한 검색 API 요청을 등록하고 request/redirect 연결을 추적한다.
- 로그인 redirect는 해당 요청의 응답 Location 또는 실제 redirect chain으로 확인한다. nid 도메인의 무관한 이미지·iframe·추적 요청만으로 로그인으로 판정하지 않는다.
- CORS/ERR_FAILED 메시지만으로 로그인이라고 단정하지 않는다. redirect 근거가 없으면 통신 실패/무응답으로 기록한다.
- CDP URL 차단으로 Playwright에서 후속 요청이 누락되는 상황을 모의 브라우저로 검증한다. 필요 시 기존 CDP의 네트워크 이벤트를 읽기 전용으로 보완한다.
- 요청 차단 정책·캐시·헤더·인증 상태는 바꾸지 않는다. 로그인 페이지 허용, 쿠키 삭제, 자동 로그인, 대체 API, 프록시 등을 추가하지 않는다.
- 시도 종료 후 리스너·탭·팝업 참조를 정리한다. 종료된 시도의 늦은 이벤트가 새 시도에 영향을 주지 않도록 시도 식별자를 확인한다.
- 동일 문제의 response/requestfailed/timeout 중복 이벤트는 한 번만 집계한다. 명시적인 보안 제한은 일반 무응답보다 우선한다.

## 4. 대기·재개와 동시성

1. 대기 사유가 확인되면 브라우저 전용 스레드에서 검색 전용 Chrome의 네이버 탭을 정리한다. 무관한 탭·개인 Chrome은 유지하고 빈 탭 하나를 남긴다.
2. 탭 정리가 확인된 뒤 짧은 DB 트랜잭션에서 시도 기록, 재개 시각, 현재 상품 PENDING, 작업 RETRY_WAIT를 저장하고 점유를 해제한다. 탭 정리 실패 시 수동 중단한다.
3. 기존 5초 폴링으로 예정 시각 이후 중단 상품부터 새 탭에서 홈 → 검색을 재실행한다. 긴 sleep이나 즉시 재클릭은 사용하지 않는다.
4. 60초 간격과 휴식 종료 시각 중 더 늦은 시각을 지킨다. 휴식 뒤 별도의 60초를 덧붙이지 않는다. 실패 처리나 오래된 콜백이 긴 휴식 시각을 60초로 줄이지 못하게 한다.
5. 작업의 선호·선정·검색 기준 스냅샷과 완료 상품을 유지한다. 진행 중인 불완전한 검색은 캐시에 저장하거나 재고 조회에 전달하지 않는다.
6. 대기 중 사용자 중단·취소가 우선한다. 예정 시각 전 즉시 재개를 서버에서도 차단한다.
7. 작업 취소 후 새 작업/예약/실패 재조회로 휴식을 우회하지 못하도록 검색 공통 차단 시각을 저장한다. 최종 자동 중단은 공통 수동 재개 필요 상태로 유지하고 명시적 재개만 새 주기를 시작한다.
8. 개별 재고 대기열도 기존처럼 검색 중단/대기 동안 실행하지 않는다. 작업 취소 후에도 공통 대기/수동 차단을 검사한다. 새 작업 접수와 실제 실행 가능 여부를 구분한다.
9. 서버 재시작·다중 워커·점유 만료에서 중복 재개/중복 횟수 증가를 막는다. 사용자 취소나 점유 상실 시 늦게 도착한 결과를 저장하지 않는다.
10. 외부 검색 스레드의 종료/탭 정리가 확인되기 전에 새 검색을 시작하지 않는다. 특히 180초 future 취소 후에도 실제 브라우저 작업이 남는 경우를 검사한다.

## 5. 저장·로그·화면

기존 RETRY_WAIT/BLOCKED와 워커·알림을 재사용한다. 기존 마이그레이션은 고치지 않고 다음 새 마이그레이션에서 일반화한 검색 재시도 상태와 검색 시도 진단 저장을 추가한다.

- 작업: 일반 검색 재시도 횟수·최근 원인·재개 예정. 기존 loginRetryCount는 호환 필드로 남기고 의미를 몰래 무응답 횟수로 바꾸지 않는다.
- 공통 검색 설정: 작업 간 유지하는 휴식 종료 시각, 수동 재개 필요 상태, 원인이 된 작업/시도 참조. 기존 next_search_at과 중복 의미를 명확히 나눈다.
- 시도 진단: 시도 ID, 작업/상품 ID, 단계, 원인 코드, HTTP 상태, 요청 발생/응답 수신 여부, 검증 불일치 항목, 발생/종료 시각, 적용한 휴식, 최종 처리. 동일 시도 한 번만 저장한다.
- 검색어는 기존 작업 항목으로 연결한다. 로그에는 검색어/응답 전문 대신 작업·상품·시도 ID, 단계, 코드, 소요 시간, 예상/관측 정렬·페이지·개수, 검색어 일치 여부만 남긴다.
- 쿠키·인증 헤더·전체 URL 쿼리·응답 전문·원본 내부 예외 메시지를 화면에 저장하지 않는다. 안전한 원인별 문구를 사용한다.
- 화면: `네이버 검색 응답 지연 · 5분 후 재개 예정`, `네이버 로그인 요구 · 30분 후 재개 예정`, `검색 응답 검증 반복 실패 · 수동 확인 필요`. RETRY_WAIT를 무조건 로그인이라고 표시하는 현행 JS를 함께 변경한다.
- 상품 상세 스피너는 대기 시 멈추고 예정 시각/작업 링크를 표시한다. 작업 화면에서 시도별 원인과 대기 내역을 확인한다.
- 대기·최종 중단 알림은 작업 전환당 한 번. 세부 네트워크 이벤트마다 알림을 추가하지 않는다.

## 6. 추천 실패·재조회 대상 분리

- 롯데홈쇼핑 추천 단계의 403/418/429는 해당 작업의 동일 쇼핑몰 추천 요청을 생략하는 정책을 유지한다. 네이버 검색 휴식 횟수에 포함하지 않는다. 모든 4xx를 접속 제한으로 확대하지 않는다.
- 옵션 미확인은 정상 응답에서 재고 구조/수량을 확정하지 못한 상태다. 쇼핑몰 접속 제한이 아니므로 다른 판매글 요청을 일괄 중지하지 않는다. 더현대Hi 김포점의 실제 원인은 해당 응답 자료로 별도 확인해야 한다.
- 미확인 상태를 임의 품절로 바꾸거나 김포점 전체를 제외하지 않는다. 필요하면 옵션 파서 문제를 별도 작업으로 조사한다.
- 73건 같은 안내는 `검색 실패 / 재고 확인 필요 / 비교 결과 없음 / 기타 재조회 필요`로 나눠 보여준다. 추천 실패·제한 생략은 별도 집계다.
- 기존 재조회 대상 범위는 이번에 몰래 변경하지 않는다. 특히 NO_MATCH는 오류 없는 정상 결과일 수도 있음을 표시한다. 화면 건수와 재조회 API 대상은 동일 조건을 공유하도록 정리한다.
- 휴식 중 상품은 최종 실패로 확정하지 않는다. 성공하면 최종 작업 결과는 성공이며, 대기했던 사실은 시도 기록에만 남긴다. 작업 마지막에 모든 실패를 한 번 더 돌리는 중복 자동 재시도는 이번 범위에 넣지 않는다.

## 7. 가격·재고 변동 기록 보호

- 대기 진입은 관측값이 아니다. 가격/재고 0, 품절, 미발견, 옵션 삭제, 신규 판매글 등의 변동 이벤트를 만들지 않는다.
- 이전 정상 값·확인 시각·선정·사용자 검토 기준은 보존하고 이전 확인값이라는 표시만 유지한다. 재시도 성공 결과만 한 번 확정한다.
- 검색 실패/중단으로 미발견을 만들지 않는다. 정상 검색과 확인된 재고만 기존 변동 계산으로 전달한다.
- 결과 확정과 확인 완료가 경합하면 기존 변동 버전 충돌 검사를 유지한다. 대기 중 확인 완료를 허용하여 보지 못한 결과까지 확인한 것으로 만들지 않는다.
- 휴식 중 선호/선정 변경, 검색어 수정, 삭제/통합은 기존 잠금·스냅샷·버전 규칙을 따른다.
- 캐시를 재사용해도 원래 가격/재고 확인 시각을 유지한다. 오래 쉰 뒤 캐시 만료 시 새 검색을 하되 완료 상품을 재처리하지 않는다.

## 8. 검증과 적용 순서

1. 운영 작업 892380783276764856의 읽기 전용 집계는 완료했다(1절). 과거 원인을 추정해서 덮어쓰지 않는다.
2. 모의 브라우저로 API → 로그인 302/CORS 실패, 요청 자체 없음, 응답 무기한 지연, 잘못된 정렬/검색어, 필수 요소 누락, 무관한 nid 요청을 재현한다. 실제 네이버에 반복 제한을 유발하지 않는다.
3. 구조화 진단과 제한적인 감지를 구현하고, 기존의 확실한 제한 감지·상품 응답 검증이 유지되는지 확인한다.
4. 같은 수정 범위에서 DB 대기·재개·공통 차단·UI 문구·개별 조회 차단을 연결한다. 감지 코드만 바꾸고 수명주기 검증을 생략하지 않는다.
5. 가상 시계로 전체 재시도 단계, 혼합 원인, 성공 초기화, 캐시 미초기화, 재개 시 추가 60초 없음, 최종 중단과 수동 재개를 검증한다.
6. 임시 MySQL에서 중복 이벤트/워커, 재시작, 취소와 자동 재개의 경합, 새 작업 우회 차단, 시도 저장 중복 방지를 검사한다.
7. 가격·재고·선정·검토 기준·미발견 이력에 대기/실패가 잘못 반영되지 않는지 검사한다. 추천 403 정책, 대표 재고 생략, 40건 한도, 기본 3페이지도 회귀 검증한다.
8. QHD/모바일에서 원인별 대기 문구, 상품 대기와 실패의 구분, 작업 진단/집계/버튼을 확인한다.
9. 진행 중 작업 상태를 확인한 뒤 안전한 경계에서 적용한다. 기존 수동 중단 작업을 자동으로 깨우지 않는다. 소수 상품으로 한 차례 확인한 후 전체 최신화에 적용한다.

이번 범위는 네이버 검색 복구와 원인 진단이다. 네이버 휴식 시간을 쇼핑몰 전체 장애 정책으로 확장하거나, 옵션 미확인 파서·자동 영구 제외·장애 알림 체계를 동시에 변경하지 않는다.


## 9. 구현 단위와 계약 확정

### A. 검색 시도 진단

`NaverSearchPayload`가 검증 실패 이유를 제공하도록 내부 결과를 구조화한다. 가격 데이터 수용 조건은 유지한다. `NaverPriceSearch`에는 단계(HOME, SEARCH_RESULTS, SORT, PAGE_SIZE, SMART_PRICE, PAGING), 활성 요청, 시도 ID를 연결한다. 네트워크 계층은 관측 신호를 전달하며 DB 상태를 직접 변경하지 않는다.

요청·응답 전체를 저장하지 않고 한 시도 내 제한된 진단 요약을 만든다. 이번 클릭 이후의 요청인지, 이전 정렬/페이지의 잔여 응답인지를 구분한다. 단순히 무관한 응답이 도착했다는 이유로 RESPONSE_MISMATCH로 오분류하지 않는다. 실제 요청/응답과 연결하지 못한 경우는 근거 불명확으로 남긴다.

### B. 영속 상태와 원인별 재개

예정 마이그레이션: `V21__naver_search_recovery.sql`(구현 시작 시 최신 번호 재확인).

- `product_search_attempt`: id, run_id, product_id, lookup_revision, attempt_no, owner_token, status, stage, reason_code, http_status, safe_diagnostics JSON, started_at, finished_at, retry_at. `(run_id,product_id,attempt_no)` 유일 제약. 활성 시도와 소유권을 검사한 뒤 한 번만 종료한다.
- 작업: `search_retry_count`, `last_search_attempt_id`, 필요 시 동일 검증 오류 재현을 판단할 안전한 signature. 기존 `block_reason`과 `next_retry_at` 재사용.
- 공통 설정: `search_cooldown_until`, `search_manual_resume_required`, `search_gate_attempt_id`, `search_gate_version`. 기존 `next_search_at`은 검색 완료 후 60초 최소 간격으로 의미를 유지한다.
- 새 단계 횟수는 로그인/무응답을 통합하되 legacy `login_retry_count`는 실제 로그인 감지 횟수로 유지한다. 기존 활성 로그인 대기의 단계·예정 시각을 새 필드로 이관하고 자동 깨우지 않는다.
- 오래된 BLOCKED/PAUSED 작업에 새 재개 시각을 만들어 주지 않는다. 과거 FAILED에 자동 재시도를 소급 등록하지 않는다.

작업과 공통 gate, 진단을 기존 DB 잠금 안에서 함께 반영한다. gate 해제는 해당 버전/시도를 대상으로 하며, 이전 시도의 성공/종료 콜백이 새 차단을 해제하지 못한다. 일반 60초 간격 갱신은 cooldown을 변경하지 않는다.

검색 시도 시작을 요청 전에 저장한다. 프로세스가 실행 도중 종료되면 RUNNING 시도를 성공/실패로 추정하지 않는다. 점유 만료 후 INTERRUPTED로 기록하고, 안전 대기 5분과 미확정 브라우저 정리를 거친 후 재시도한다. 재시작 자체를 로그인 감지로 세지 않는다. 브라우저 정리나 소유권 확인이 안 되면 수동 중단한다.

### C. API·UI

- 기존 작업/상품 상태 API에 `searchRetryCount`, `searchFailureStage`, `searchFailureCode`, `searchCooldownUntil`, `manualResumeRequired`를 추가한다. 기존 `nextRetryAt`, `blockReason`, `loginRetryCount`는 유지한다.
- 작업별 시도 이력: `GET /api/product-refresh/{id}/search-attempts`를 추가한다. 기존 작업 API의 하위 경로를 따른다. 페이지 단위 조회와 상품/원인 필터를 제공한다. ID 문자열·ApiResponse·기존 권한을 유지한다.
- 기존 resume/pause/cancel 사용. 작업 취소 후에도 남는 공통 수동 차단을 해제하기 위해 `POST /api/product-refresh/search-gate/resume`을 제공한다. 연결된 활성 작업이 있으면 기존 작업 resume과 동일한 제약으로 처리하고, 취소된 작업은 되살리지 않는다. gate 버전과 현재 actor 권한·CSRF를 검사하고, 남은 대기 시각 전 해제를 거부한다. 임의 URL이나 클라이언트 시각은 받지 않는다.
- 상품별 결과와 전체 작업의 카운트는 서로 다른 단위를 표시한다. 상품 상태 수(56/12/5)와 추천 판매글 실패·생략 수(1/54)를 섞지 않는다.
- 기존 ‘실패 재조회’ 버튼은 대상 범위를 유지하면서 ‘대상 재조회’로 이름을 정리하고, 확인 화면에 오류가 아닌 ‘비교 결과 없음’ 포함 여부를 명시한다. 향후 대상 선택 기능은 별도 범위다.
- UI는 원인 코드로 문구를 선택한다. 일반 화면에는 간단한 원인·예정 시각, 펼친 시도 이력에는 단계·횟수·처리를 표시한다.

### D. 저장 경계·검토 버전

워커가 대기로 전환할 때 `finish(FAILED)`를 호출하지 않는다. 불완전 검색 결과로 supplier/observation/review/last_good_result를 갱신하지 않는다. 성공 확정 경로의 기존 트랜잭션에서만 변동을 저장한다.

기존 코드의 CHECKING 시작 시 latest_result를 비우는 표시 정책을 고려해, 정상 선정값은 기존 selected/last_good 경로로 계속 보여준다. 대기를 정상 최신 확인값처럼 표시하지 않는다. 선택·검색 기준이 바뀌면 늦은 시도는 STALE/CANCELLED로 종료하고 새 관측에 반영하지 않는다.

### E. 배포 승인 기준

- 같은 정렬 무응답 모의 사례에서 기존 FAILED→다음 상품 대신 RETRY_WAIT→동일 상품 재개가 확인된다.
- 로그인 redirect 증거가 있는 경우만 로그인 원인으로 기록된다. 무관한 nid 요청과 예전 탭 이벤트는 횟수에 영향을 주지 않는다.
- 원인 교대, 캐시 사용, 프로세스 재시작, 두 워커, 사용자 취소, 최종 수동 재개를 모두 검증한다.
- 취소 후 새 작업·예약·개별 조회에서 공통 대기를 우회하지 못한다. gate 화면이 없어 수동 해제가 불가능한 상태를 만들지 않는다.
- 네이버 403/보안 확인과 쇼핑몰 추천 403의 중단 범위가 바뀌지 않는다.
- 관측·선정·확인 시각·검토 기준 해시가 대기 전후 동일하며, 재시도 성공 후 새 관측은 한 번만 생성된다.
- 정상 기본 3페이지는 특수 이벤트·안내·오류를 생성하지 않는다. 검색 간격 60초·클릭 3초·안정화 2초·대표 재고 생략·추천 40건 제한은 유지한다.

구현은 A~D를 하나의 기능 단위로 검증하고 배포한다. 진단만 먼저 내부 모의 환경에서 확인할 수 있으나 운영에서 실제 제한을 반복 유발하여 검증하지 않는다. 승인한 A~D의 마이그레이션·API·실행 코드·UI 구현과 격리 검증을 완료했다. 실제 응답에 근거가 없는 과거 실패 원인을 소급 변경하지 않았다.
