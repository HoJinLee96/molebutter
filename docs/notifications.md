# 사용자별 알림

V15는 `notification_event`(사건)와 `user_notification`(수신·개별 삭제), 최신화 작업의 알림 순번을 추가한다. 기존 결과를 소급 생성하지 않는다. 숫자는 미삭제 개수이며 읽음 상태나 자동 만료는 없다.

## 생성

- `NotificationService.publish`는 진행 중인 업무 트랜잭션을 요구한다. 성공과 알림이 함께 커밋된다. 사건 키는 유일하고 삭제한 수신 행도 유지하여 재처리로 되살아나지 않는다.
- 최신화 완료/접속 제한/취소는 실제 서버 상태 전환에서 한 건씩 발생한다. 예약 수신자는 사건 발생 당시 ACTIVE ADMIN/PRODUCT, 수동 작업은 최초 실행자다. 재개 후 다시 제한되면 다음 순번의 별도 사건이다.
- 엑셀 등록은 등록 건수 요약 한 건, 근태 정정 신청/취소는 본인, 승인/반려는 본인과 처리 관리자에게 전달한다.
- 일반 저장·출퇴근 성공, GET, 폴링, 시작·재개는 영구 알림을 만들지 않는다.
- `OperationFailure`와 낙관적 수정 충돌, 예상하지 못한 서버 예외만 최종 실패 알림 대상으로 분류한다. 필수 입력·형식·인증·CSRF 오류는 제외한다. 화면용 안전한 메시지만 저장한다.
- 실패는 MVC 예외 처리에서 업무 롤백 후 `REQUIRES_NEW`로 저장한다. 알림 저장 실패는 로그로 남기고 원래 오류 응답을 유지한다. `X-Operation-Id`는 브라우저의 동일 요청 재시도에서 유지하며, 비로그인·알림 API 자체에는 실패 알림을 만들지 않는다.

## API

모두 최신 계정 상태와 수신자 소유권을 검사한다. 기존 ApiResponse를 사용하며 모든 ID는 문자열로 반환한다.

- GET `/api/notifications?cursor=...&size=20`: 삭제 전 항목만 내림차순. 최대 50개. `items`, `nextCursor`.
- GET `/api/notifications/summary`: `count`, `latestId`.
- GET `/api/notifications/{id}/target`: 서버가 결정한 `url` 또는 이동 불가 `reason`. 읽음/삭제 부수 효과 없음.
- DELETE `/api/notifications/{id}`: CSRF 필수. 자신의 삭제 시각만 기록하며 반복 삭제도 성공.

권한을 잃은 업무는 내용을 가리고, 개수에는 포함하며 삭제는 허용한다. 대상 ID는 외래키로 연결하지 않아 상품 삭제 후에도 알림이 유지된다. 업무 대상은 이동 시 다시 검사하며 외부 주소는 반환하지 않는다. 로그인 전 페이지에는 종이 없다.

## 화면

15초 가시 탭 폴링, 진입/포커스 복귀/변경 요청 완료 시 요약 갱신. 최초 접속의 과거 알림은 팝업하지 않는다. 패널은 커서로 20개씩 추가한다. 새 결과 팝업은 5초 후 사라지지만 수신 기록은 유지된다. X는 서버 성공 후 반영하며 실패는 패널 내부에 표시한다. 종 버튼은 공통 사이드바에 표시하며 모바일에서는 메뉴를 열어 접근한다. 업무 모달에는 종 버튼을 추가하지 않고, 모달이 열린 동안 새 알림 팝업도 표시하지 않는다. 알림 저장과 개수 갱신은 유지한다.

상세 이동: `/products?product=ID`, `/product-refresh?run=ID`, `/attendance?correction=ID`, `/attendance-manage?correction=ID`. 엑셀 알림은 `/products#import-panel`. 입력한 폼이 남아 있으면 이동 확인을 한다. 원본 엑셀은 저장하지 않는다.

## 검증

`ProductFlowIT`의 알림 테스트는 롤백/중복/커서/개별 삭제/재개 후 재발행/권한/CSRF/엑셀/정정 결과를 검증한다. `MigrationUpgradeIT`는 V14→V15 전환과 기존 선정 데이터를 확인한다. `scripts/test-notifications-ui.cjs`는 모의 API와 실제 화면 코드로 1440px·390px에서 알림 진입·이동·삭제·오류 복구와 키보드 동작을 검증한다. 운영 DB 및 외부 쇼핑몰은 사용하지 않는다.
