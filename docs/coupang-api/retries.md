# 쿠팡 API 공통 재시도

상품 등록·승인·수정·가격·수량·판매상태·삭제와 상품·옵션·카테고리·브랜드·물류·주문·클레임 조회는 `CoupangProductClient`의 같은 HTTP 실행기를 사용한다. 브랜드 검색과 반품철회 목록 조회는 HTTP POST지만 읽기 계약으로 실행한다. 새 엔드포인트·테이블·마이그레이션·주기 작업은 없다.

## 대기와 범위

- 모든 연속 요청의 공통 간격은 **이전 응답을 받은 뒤 최소 2초**다. 아래 신규 등록·승인 결과 확인에는 5초 예외를 적용한다. 상품 등록·승인·가격·재고 수정 후 결과 조회뿐 아니라 연속 조회·읽기 POST·삭제·오류 응답 이후에도 같은 계정의 공통 대기를 적용한다. 느린 응답의 처리 시간을 대기 시간으로 세지 않으며, 작업 세션이 끝나도 다음 요청에 대기가 이어진다. 첫 요청은 즉시 가능하고 이미 2초가 지났으면 추가로 기다리지 않는다. 네트워크 오류·타임아웃 뒤에도 실패가 반환된 시점부터 2초를 지킨다. 일시적 실패의 재시도는 최대 1회(최초 포함 2회)이며 여러 오류가 이어져도 예산을 다시 시작하지 않는다.
- **신규 상품 등록 성공 → 최소 5초 대기 → 승인 요청 → 승인 성공 → 최소 5초 대기 → 결과 조회**는 자동으로 진행한다. `CoupangProductClient.withFirstResponseGap`에서 해당 호출의 첫 실제 전송에만 5초를 적용하며 공통 2초 제한·로그를 그대로 거친다. 기존 상품 수정의 승인·가격/재고 수정 후 조회·카탈로그/주문 조회 및 HTTP 자동 재시도는 2초다. 5초 범위는 성공·실패·취소·호출 전 예외에서 해제되며 다른 요청으로 전파하지 않는다. 대기 중 취소와 더 긴 서버 대기는 유지한다. [신규 등록 5초 예외 검증](../verification/2026-10-21-coupang-create-five-second-gap.md), [전체 호출 간격 검증](../verification/2026-10-21-coupang-all-response-gap.md), [등록·승인 간격의 이전 검증](../verification/2026-10-21-coupang-approval-response-gap.md)
- 신규 등록 승인 성공 후 GET이 상품 처리 중이거나 승인 대기이면 RUNNING 상태에서 다음 GET을 5초 간격으로 자동 실행한다. 브라우저는 앱 DB 상태만 폴링하며 쿠팡 재조회 버튼을 자동 클릭하지 않는다. 10분·최대 120회의 확인 예산을 사용하며 각 GET의 기존 HTTP 재시도 예산은 그대로다. 등록 POST·승인 PUT은 반복하지 않는다. 승인 반려·식별자/옵션 연결 이상·권한/취소·그 외 조회 실패는 자동 확인을 중단하고 기존 성공 접수와 ID를 보존한다. 한도 종료는 자동 확인 시간 초과로 표시한다. 임대 heartbeat·계정 잠금은 작업 중 유지하며 종료·재시작은 기존 UNKNOWN 결과 확인 보호를 따른다. ACCEPTED 신규 승인 단계의 명시적인 결과 확인에도 같은 자동 확인을 사용하며 UNKNOWN·기존 상품 편집의 별도 결과 확인은 공통 간격을 사용한다. [자동 확인 지속 검증](../verification/2026-10-21-coupang-approval-auto-lookup.md#후속-수정-처리-중에도-자동-get-계속)
- `Retry-After`의 초·HTTP 날짜가 더 길면 그 시간을 우선한다. 30초를 넘으면 인라인 재시도를 하지 않고 기존 오류를 반환한다. 같은 클라이언트의 후속 호출에도 서버 대기 시간을 적용한다. 헤더가 없거나 유효하지 않으면 2초다. 유효한 헤더가 2초보다 짧아도 최소 2초를 지킨다.
- 조회는 네트워크 오류·타임아웃·HTTP 408·5xx·429와 명확한 상품 등록/수정 처리 중 응답을 재시도한다.
- 쓰기는 HTTP 429 또는 HTTP 200 `code=ERROR`/HTTP 400의 명확한 상품 처리 중 거절만 재시도한다. 승인 경로에는 실제 확인된 `임시저장 상태의 상품만 승인 요청 가능합니다.` 거절도 포함한다. 중첩 `code=200,data.code=ERROR` 응답도 판독한다. ERROR인데 상품 식별자 등 `data`가 반환된 쓰기는 자동 재전송하지 않는다.
- 인증·권한·필수값·상품 없음·삭제 등 영구 오류와 모르는 거절 문구는 자동 재시도하지 않는다. 쓰기의 타임아웃·네트워크 유실·5xx·잘못된 응답은 처리 여부가 불명확하므로 기존 UNKNOWN/결과 확인 보호를 유지한다. SUCCESS·ACCEPTED는 재전송하지 않는다.

수집한 공식 SOURCE(2026-10-03)는 상품 처리 중인 특정 오류에 대해 최소 10분 후 조회/승인 재시도를 안내한다. 사용자 요청에 따라 승인 성공 후에는 5초 간격의 GET 확인을 최대 10분 수행하는 앱 정책을 사용한다. 승인 PUT의 명확한 거절은 기존 1회 재시도와 처리 중 오류·10분 후 승인 재시도 안내를 유지한다. 자동 GET이 처리 완료를 보장하지 않는다. 공식 문서 자체를 변경하거나 앱의 2초·5초 대기로 처리 완료가 보장된다고 해석하지 않는다.

## 전송 보호

명확히 거절된 요청을 다시 보낼 때도 같은 요청 내용과 확정된 상품 ID를 사용한다. 등록 성공 후 승인이 거절됐다고 CREATE를 다시 보내지 않는다. 매 시도마다 서명을 새로 생성하고 취소를 확인한다.

쓰기 재시도 직전 권한, 계정 임대와 기존 `beforeDispatch` 검사(빠른 수정의 선정 근거 fingerprint·충돌 검사 포함)를 다시 수행한다. 일반 수정·가격·수량은 상품/옵션 연결과 최초 전송 직전 기준값을 다시 대조하고, 값이 바뀌면 입력을 보존한 채 재확인을 요구한다. 신규 등록은 서버 보관 카테고리 규격의 10분 유효시간과 준비 시각을 확인하며 판매자상품코드를 조회하지 않는다. ID가 없는 UNKNOWN 등록의 결과 확인도 외부 후보 조회 없이 Wing 직접 확인을 안내한다. 삭제는 상품 구성과 모든 옵션 판매중지 상태를 다시 확인한다. 재시도 직전 보호 검사에 추가 조회가 필요하면 그 조회 응답 이후에도 2초를 기다리므로 전체 재전송 대기는 더 길 수 있다.

## 로그와 DB

모든 실제 전송 시도는 공통 실행기에서 `[COUPANG_API] event=START`와 `event=RESPONSE` 또는 `event=FAILURE`를 한 쌍으로 남긴다. 첫 성공도 생략하지 않는다. `request`는 임의로 생성한 추적 ID이며 재시도는 같은 ID와 증가한 `attempt`를 사용한다. 서로 다른 호출과 재시도 직전의 보호 조회는 별도 ID다. `execution`·`step`은 전송 워커 안에서 연결하며 단순 조회에서는 `-`다. `operation`·`method`로 등록·승인·가격·재고·현재 옵션 재고·판매상태·삭제·카탈로그·배송지·주문·반품·교환·철회 종류를 구분한다. 실제 요청 경로·쿼리·본문은 남기지 않는다.

| 필드 | 의미 |
|---|---|
| `startedAt` | 전송 시도 직전 시각. `+09:00`을 명시한 한국 시각 |
| `responseAt` | 응답 본문 수신 완료 시각. 응답 없이 실패했으면 `-` |
| `finishedAt` | 응답 완료 또는 전송 실패가 반환된 시각 |
| `durationMs` | 시도 시작부터 완료까지 걸린 시간 |
| `previousResponseAt`, `sincePreviousResponseMs` | 직전 HTTP 응답 수신 완료와 이번 시도 시작 사이의 간격. 첫 호출·아직 응답 없는 경우 `-` |
| `previousFinishedAt`, `sincePreviousFinishMs` | 직전 응답 또는 네트워크 실패 완료부터의 간격. 실패 이후 2초 대기 확인에 사용 |
| `paceWaitMs` | 이번 시도의 공통 호출 간격 검사에서 실제 기다린 시간. 업무 처리·자연 유휴·보호 조회 시간은 제외 |
| `http`, `code`, `decision` | HTTP 상태, 고정 판독 결과, `RETRY` 또는 `STOP`. HTTP 응답 없이 실패하면 `http=0` |

소요 시간과 간격은 단조 시계로 계산하며 밀리초 미만은 버린다. 시스템 시각 변경과 별개로 2초 간격을 검사할 수 있다. 서버 `Retry-After` 대기와 재시도 보호 검사 시간이 포함되면 응답 사이 간격은 `paceWaitMs`보다 길 수 있다. 전송 전 취소·권한·입력 검사에서 막혀 클라이언트를 호출하지 않은 작업은 실제 전송 시도 로그를 만들지 않는다. 캐시 재사용에도 호출 로그는 없다.

START 뒤 아직 완료 로그가 없으면 대기 중이거나 프로세스가 중단됐을 수 있다. START만으로 쿠팡의 실제 처리 성공·실패를 판단하거나 쓰기를 재전송하지 않는다. 첫 시도를 포함한 호출 수는 START 수이며, 재시도 횟수는 같은 `request`의 `attempt`로 구분한다.

- INFO: 모든 시도 시작, 첫 성공·재시도 후 복구를 포함한 정상 응답.
- WARN: 쿠팡의 업무 거절·인증/권한 거절·호출 제한, 재시도 예정인 일시적 통신/서버 오류, 취소.
- ERROR: 최종 네트워크/타임아웃·서버 오류, 잘못된 JSON/알 수 없는 응답 형식, 예상하지 못한 클라이언트 예외. 예외 메시지·원인·스택은 이 로그에 포함하지 않는다.

`code=SUCCESS`는 해당 HTTP 응답의 결과 봉투를 판독한 결과다. 상품 승인 완료나 후속 업무·전체 필드 검증 성공을 뜻하지 않는다. 주문·반품지의 숫자/문자열 `200`, 출고지의 `content/pagination`, 중첩 결과 등 현재 지원하는 응답 형식을 구분한다. 잘못된 카테고리 내용처럼 후속 검증에서 발견한 문제는 기존 검증 로그·전송 결과에도 남는다. 키·서명·Authorization·계정·주문/개인정보·응답 본문·쿠팡 자유 문구는 출력하지 않는다.

현재 호출 로그와 검증 범위는 [2026-10-21 전체 호출 로그 검증](../verification/2026-10-21-coupang-api-logging.md)을 따른다.

쓰기의 최종 결과와 민감정보를 제거한 거절 사유는 기존 실행 단계·attempt·전송 기록에 보존한다. 내부 HTTP 재시도 때문에 새 실행을 만들지 않으며, HTTP별 시도 번호는 로그에서 구분한다. 조회 실패는 기존 조회 오류/수집 실패 처리로 전달한다. 모든 일회성 조회를 별도 DB 테이블에 저장하지 않는다. DB 커밋 실패·UNKNOWN·ACCEPTED의 중복 전송 보호를 유지한다.

검증 범위와 결과는 [2026-10-19 검증 기록](../verification/2026-10-19-coupang-api-retry.md)을 확인한다. 운영 DB·실행 중인 IDE 앱·실제 쿠팡 값에 적용하거나 전송한 결과와 구분한다.
