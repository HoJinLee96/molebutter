# 근태 기록·관리자 집계·정정 승인

> 문서 유형: 현재 구현 안내. 2026-10-05 로컬 코드와 대조했다. 날짜가 붙은 적용·검증 문단은 당시 기록이며 현재 정책과 구분한다.

## 이용 방법

- 홈 또는 상단 **근태** 메뉴에서 출근·휴게 시작/종료·퇴근을 기록한다. 시각은 서버의 `Asia/Seoul` 기준이다.
- 하루 한 번 출근할 수 있다. 자정 이후에도 이전 근무 퇴근이 가능하며 출근 날짜로 기록된다.
- 전날 근무가 진행 중이면 **이전 근무 퇴근**과 **오늘 출근**을 구분한다. 오늘 출근을 확인하면 이전 기록은 퇴근 누락으로 남고 새 기록이 생성된다. 누락된 시각과 열려 있던 휴게 종료 시각은 자동으로 채우지 않는다.
- 휴게 중 퇴근하면 해당 시각에 휴게도 종료한다. 근무 중 시간은 진행 중 값이며, 퇴근 누락 기록의 근무시간은 미확정이다.
- 근태 기록은 선택한 월을 날짜 역순으로 20건씩 조회한다. 기록 상세에서 휴게 구간과 정정 신청을 확인한다.
- 현재 진행 중인 근무는 먼저 마감한다. 종료·누락 기록은 상세의 **정정 신청**, 기록 자체가 없는 날짜는 **누락일 정정 신청**을 이용한다.
- 신청에는 출근 날짜, 출퇴근 시각, 전체 휴게 구간, 사유를 입력한다. 승인 대기 요청은 같은 날짜에 하나만 허용하며 취소 후 재신청할 수 있다.
- 관리자의 **근태 관리 → 정정 요청**에서 요청을 검토한다. 변경 전후를 비교한 뒤 승인 또는 반려한다. 반려 사유는 필수이며, 관리자 본인 요청도 승인할 수 있다.
- 승인된 요청의 원본·제안·처리자·처리 시각은 보존된다. 후속 정정이 있어도 이전 요청 내용은 바뀌지 않는다.

위치 제한, 결근/지각/연장근무 판정과 급여 계산은 포함하지 않는다. 정정 신청·취소·승인·반려 알림은 [알림](notifications.md)의 규칙을 따른다. 로그인 후 기본 홈 이동은 유지한다.

## 관리자 조회와 CSV

`/attendance-manage`는 **전체 기록 / 월별 집계 / 정정 요청** 세 탭으로 구성한다.

- 전체 기록: 시작일·종료일(양 끝 포함 최대 366일), 직원 이름/이메일, 근태 상태로 검색한다. 기본값은 한국 시간 기준 당월이며 근무일·ID 내림차순으로 20건씩 조회한다. 상세에서 모든 휴게 구간을 확인한다.
- 월별 집계: 월·직원으로 검색하고 직원 이름·ID 오름차순으로 20명씩 조회한다. 동명이인은 이메일과 문자열 ID로 구분한다.
- `COMPLETED`만 순근무·휴게 시간을 합산한다. 각 휴게 구간을 초 단위로 계산한 뒤 기록별로 합치므로 휴게가 여러 개여도 근무시간이 중복되지 않는다. 화면/CSV는 24시간을 넘는 `H:mm:ss`를 지원한다.
- 근무 중·휴게 중·퇴근 누락은 각각 건수로 표시하고 합계를 미확정 건수로 제공한다. 관리자 상세의 미확정 기록은 시간 합계가 null이며 CSV에서도 빈칸이다. 본인 화면의 진행 시간과는 구분한다.
- 야간 근무는 출근 날짜의 월에 속한다. 정정 승인 전에는 기존 기록, 승인 후에는 변경 기록으로 집계한다.
- 월말까지 가입한 현재 `PENDING` 이외의 직원은 기록이 없어도 표시한다. 관리자·잠금·정지 계정을 포함한다. 해당 월에 기록이 있으면 가입일·현재 상태와 무관하게 포함한다. 계정 상태는 현재 값이며 출근하지 않은 날을 결근으로 계산하지 않는다.
- CSV는 페이지와 무관하게 입력한 검색 조건의 전체 결과를 내보낸다. 다운로드 버튼은 생성 중 비활성화하고, 인증 만료·권한 부족·오류 응답·불완전한 응답을 파일로 저장하지 않는다.
- CSV는 UTF-8 BOM, 한글 제목, CRLF, 모든 셀 인용 및 큰따옴표 이중 처리를 사용한다. 휴게 구간은 한 셀에 `/`로 연결하고 종료가 없으면 `미기록`으로 표시한다. 직원 ID는 Excel 정밀도 보존을 위해 탭 접두사로 텍스트 처리한다. 이름/이메일에 수식 시작 문자나 제어 문자가 있으면 작은따옴표 접두사로 수식 실행을 막는다. CSV를 프로그램에서 읽을 때 ID의 맨 앞 탭을 제거할 수 있다.
- 조회 전용 서비스는 `REPEATABLE_READ` 읽기 전용 트랜잭션을 사용한다. CSV는 500건씩 조회해 하나의 DB 스냅샷에서 임시 파일로 완성한 후 전송한다. 생성 실패는 JSON 오류로 응답하고, 생성 실패/전송 종료 시 임시 파일을 삭제한다. 전체 결과를 서버 메모리에 모으지 않지만 다운로드 크기만큼 서버 임시 디스크 공간이 필요하다.

## API

기존 `ApiResponse`/`PageResponse`를 사용한다. ID는 문자열이며, 근태 시각은 한국 현지 시각 ISO 형식이다.

| Method | 경로 | 입력/기능 |
| --- | --- | --- |
| GET | `/api/attendance/current` | 서버 현재 시각, 진행 중인 근무, 오늘 기록 |
| GET | `/api/attendance?month=YYYY-MM&page=0` | 본인 월별 기록, 기본 당월·20건 |
| GET | `/api/attendance/{id}` | 본인 기록 상세 |
| POST | `/api/attendance/clock-in` | 일반 출근 `{}`; 전날 누락 확인 시 `previousRecordId`, `previousRevision`, `confirmMissing: true` |
| POST | `/api/attendance/clock-out`, `/break-start`, `/break-end` | `recordId`, `revision`; 실제 시각은 서버에서 생성 |
| GET | `/api/attendance/corrections?month=YYYY-MM&page=0` | 본인 정정 내역 |
| GET | `/api/attendance/corrections/{id}` | 본인 요청 상세 |
| POST | `/api/attendance/corrections` | `workDate`, 기존 `recordId/revision` 또는 null, `clockIn`, `clockOut`, `breaks: [{startedAt, endedAt}]`, `reason` |
| POST | `/api/attendance/corrections/{id}/cancel` | 요청 `revision` |
| GET | `/api/attendance-manage/records` | `from`, `to` (YYYY-MM-DD), `q`, `userId`, `status`, `page` |
| GET | `/api/attendance-manage/records/{id}` | 관리자 기록 상세·직원 정보·휴게 구간 |
| GET | `/api/attendance-manage/summary` | `month` (YYYY-MM), `q`, `userId`, `page` |
| GET | `/api/attendance-manage/records.csv` | 기록 검색 조건 전체 결과; page는 사용하지 않음 |
| GET | `/api/attendance-manage/summary.csv` | 월별 집계 검색 조건 전체 결과; page는 사용하지 않음 |
| GET | `/api/attendance-manage/corrections?status=PENDING&page=0` | 관리자 목록, 상태 생략 시 전체 |
| GET | `/api/attendance-manage/corrections/{id}` | 관리자 요청 상세 |
| POST | `/api/attendance-manage/corrections/{id}/approve`, `/reject` | 요청 `revision`, `comment` (반려 시 필수) |

`record`/`before`/`after`는 출퇴근 시각·상태·휴게 구간을 포함한다. 기록 응답의 `workedSeconds`/`breakSeconds`는 누락 상태일 때 null이다.

근태 조회는 최신 DB 인증 정보를 확인한다. 본인 API는 인증된 사용자 ID만 사용하며, 관리자 API는 `PERM_ATTENDANCE_MANAGE`가 필요하다. 모든 변경은 CSRF를 검사한다. 타인 리소스는 404, 권한 부족은 403, 오래된 버전·허용되지 않는 상태 전환은 409로 응답한다. 시간·구간 검증 실패는 400이다.

## 저장과 동시 처리

- `attendance`: 사용자·근무일 유일 키, 상태와 리비전.
- `attendance_break`: 일별 기록에 속한 순서 있는 휴게 구간.
- `attendance_correction`: 요청 상태·원본 버전·변경 전후 스냅샷·처리 이력.
- 변경은 사용자 행 잠금 후 처리한다. 정정 승인은 READ COMMITTED 트랜잭션으로 소유자 확인 후 잠금을 기다렸더라도 최신 원본/요청을 읽는다.
- 중복 클릭과 다중 탭 요청은 리비전으로 검사한다. 정정 신청 이후 원본이 변경되거나 누락일 기록이 새로 생기면 승인을 거부하고 취소/반려 후 재신청하게 한다.
- 근태 변경과 승인 상태 변경은 하나의 트랜잭션이다. HTTP 작업 감사는 기존 `OperationAudit`로 기록한다.
- 전후 기록과 겹치지 않는지 신청과 승인 시 모두 검사한다. 퇴근 누락 기록은 출근 및 휴게의 마지막 확인 시각을 경계로 사용한다.

## 적용 및 검증

V1/V2/V4를 수정하지 않고 `V5__attendance_query_index.sql`을 추가했다. 이전에 삭제된 V3 번호는 재사용하지 않는다. 다음 서버 시작 시 Flyway가 `attendance(work_date, id)` 인덱스를 추가한다. 새 DB에서는 V1→V2→V4→V5 순서로 적용한다. 실제 DB에 마이그레이션을 직접 실행하거나 실제 계정의 근태 데이터를 만들지는 않았다.

```bash
bash scripts/test-integration.sh
node --test src/test/js/api.test.cjs
```

격리된 MySQL·Redis에서 Java 테스트 78개(근태 16개 포함)와 JavaScript 테스트 5개가 통과했다. 출퇴근·휴게·자정 경계·전날 누락·정정 취소/승인/반려·원본 변경 충돌·동시 처리·본인 및 관리자 권한·CSRF·계정 정지·마이그레이션을 확인했다.

Chrome의 테스트 응답을 이용한 데스크톱/모바일 화면 검증에서 출퇴근·휴게, 정정 폼·취소·검토, CSRF 헤더, 사유 HTML 이스케이프를 확인했다. 실제 서버의 두 화면 렌더링은 HTTP 통합 테스트로 별도 확인했다.

관리자 조회 검증에는 기록 없는 직원·동명이인·가입 전 월·잠금/정지/대기 상태·자정/월 경계·소수 초와 여러 휴게·미확정 제외·승인 전후 집계·필터·페이지·전체 CSV·수식/한글/따옴표/긴 ID·24시간 초과를 포함한다. 502건 CSV의 두 번째 청크 직전에 다른 트랜잭션에서 실제 정정을 승인해도 파일은 승인 전 값으로 유지되고 다음 조회에는 승인 후 값이 반영되는지 확인한다. 일반 사용자·미인증·정지 관리자 접근을 차단한다. V1→V2→V4→V5 업그레이드에서 기존 계정·근태·휴게를 보존한다.

관리자 세 탭은 테스트 응답을 사용하는 Chrome에서 데스크톱(1440px)·모바일(390px) 필터·페이징·상세·정정 승인·CSV 저장/오류/중복 클릭 방지와 페이지 가로 넘침 여부를 검증한다. 테이블은 좁은 화면에서 가로 스크롤한다.
