# V48 수정 의도·감사 이력 보존 전환

V1~V47과 역사적 지원 시그니처를 변경하지 않는다. 초기화하지 않는다. V48은 `coupang_listing_history`, `coupang_listing_history_asset`, `coupang_editor_history_link`를 각각 같은 접미사의 `legacy_coupang_*` 테이블로 이동한다. 값·ID·FK·이미지 참조와 실행된 미리보기·전송 전문·해시·중복 방지 키를 보존한다. 기존 편집 세션과 미실행 미리보기만 만료시킨다.

적용 순서는 앱·워커 중지 → 전체 DB·판매 파일 백업과 격리 복원 확인 → 사전 검사·V48 → 데이터·참조 대조 → 새 앱 재기동이다. 실행 중 주문·전송과 활성 계정 임대가 있으면 중단한다. 데이터가 있는 DB의 자동 기동 전환은 거절한다.

```sh
COUPANG_ASSETS_DIRECTORY=/absolute/path/to/coupang-assets \
  bash scripts/upgrade-coupang-intent.sh --apply /absolute/path/to/new-backup-directory
```

현재 실행 설정에서 DB 설정을 읽으며 비밀 파일을 직접 열거나 수정하지 않는다. 명령은 로컬 격리 MySQL을 생성해 전체 dump를 복원하고 모든 테이블 지문을 대조한다. DB가 참조하는 이미지 파일 누락·심볼릭 링크·백업 중 변경을 거절한다. 이미지 바이트, 보존 업무 테이블과 현재·감사 판매 테이블을 전후 대조한다. 이미 V48이 적용된 경우 재실행은 데이터를 변경하지 않는다. 기존 V47 명령은 target 47로 고정돼 있으며 V48에는 새 명령을 사용한다.

V46에서 시작한다면 먼저 [V47 오프라인 보존 전환](coupang-working-copy-migration.md)을 완료한다. 중복 미디어의 전환용 관측 입력이 남아 있으면 V48도 거절한다. 이 경우 V47 준비 전 백업을 복원하며, V48에서 앞선 전환 실패를 자동 수리하지 않는다. 이미 정상적으로 V47·V48이 적용된 설치에는 다시 준비하거나 데이터를 변경하지 않는다.

백업에는 `database.sql`, `sales-assets/`, `verified-before.txt`, `verified-after.txt`, `immutable-previews.sha256`, `preflight.txt`, `UPGRADE_COMPLETE`를 남긴다. 이전 JAR도 별도 보존한다. DDL 이후 실패하면 새 앱을 시작하거나 무조건 repair하지 말고 검증된 전체 DB·파일과 이전 JAR을 함께 복원한다. 전환 후 새 입력이 생겼다면 먼저 별도 보관한다.

이전 목록 전체 수정은 DB에서 삭제하거나 추정하지 않는다. 재진입 시 저장 입력을 보여주고 전송을 막으며, 입력을 보관한 뒤 사용자가 최신 데이터에서 수정 범위를 다시 지정한다. schemaVersion 1~3 전송 증거는 조회·결과 확인에 사용하고 새 쓰기는 schemaVersion 4 미리보기로 준비한다.

현재 판매 테이블은 24개, 감사 테이블은 11개다. 감사 이력 조회와 이미지 정리 보호는 유지하며 이력 작성 API는 제거한다. 상품업무·회원·매입·보유 재고·이동 이력·R2·매입 브라우저 프로필은 변경하지 않는다. 실제 쿠팡 쓰기는 이 전환 검증에 포함하지 않는다.

이전 자동 기동의 사전 검사 실패로 V48 실패 이력만 남은 경우에도 명령은 자동 repair하지 않는다. 검증된 전체 백업을 먼저 보존하고, 세 원본 테이블이 존재하며 감사 대상 세 테이블이 없고 V47 판매 지문이 동일함을 확인한다. 체크섬 오류가 없는 단일 실패 이력인지 별도로 확인한 후 해당 실패 기록만 정리하고 새 백업으로 다시 전환한다. DDL 적용 흔적이나 다른 오류가 있으면 전체 복원 절차를 따른다.

유지보수의 `CoupangSchema.TABLES`는 현재 `coupang_*` 허용 목록이다. 새 테이블을 추가할 때 상태·보존 감사 도구의 목록도 검토하며 알려지지 않은 표는 중단시킨다. `legacy_coupang_*`는 자동 삭제 대상이 아니고 별도 감사 영역이다. V47·V48의 데이터 존재 게이트는 회원 등 보존 데이터도 포함하므로 판매 데이터가 비어 있어도 기존 설치는 백업·격리 복원 절차를 따른다. 향후 전환의 사전 검사는 작업·단계의 QUEUED/RUNNING과 취소 진행 상태, 활성 임대를 함께 검토한다. 적용된 V48은 수정하지 않는다.
