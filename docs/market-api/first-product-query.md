# 첫 판매 상품 조회 — 프로젝트 구현·검증 준비

확인일: 2026-10-03. **구현 제안과 검증 절차**이며 현재 실행 결과가 아니다. 외부 규격은 [네이버](naver-smartstore.md), [쿠팡](coupang-wing.md), [ESM](esm-gmarket-auction.md)의 공식 링크를 기준으로 한다.

## 먼저 준비할 값

| 연결 | 필수 준비 | 별도 확인 |
|---|---|---|
| 네이버 | clientId, clientSecret, SELF 앱 | 상품 API 그룹·허용 IP |
| 쿠팡 | vendorId, accessKey, secretKey | 허용 IP·180일 만료·권한 반영·마켓플레이스/그로스 |
| ESM 공통 | 승인 키, masterId, issuer | API 권한·허용 IP·운영 승인·키 형식 |
| G마켓 | ESM 공통 값 + G 판매자 ID | G 사이트 상품에 대한 접근 |
| 옥션 | ESM 공통 값 + A 판매자 ID | A 사이트 상품에 대한 접근 |

실제 값은 서버 환경 변수나 별도 비밀 설정에서 주입한다. 첫 단계에서 키 저장 CRUD나 DB 테이블을 만들 필요는 없다. 문서·Git·PR·테스트 fixture에는 예시 자리 표시만 사용한다. 브라우저에서 마켓 API를 직접 호출하지 않는다.

등록 IP는 사설 주소·localhost가 아니라 API 서버에서 관측하는 외부 출구 IP다. 로컬 Mac과 운영 서버의 IP가 다를 수 있으므로 실행 장소를 먼저 정한다. 자격 증명은 채팅에 붙이지 않는다.

## 최소 구현 범위

현재 프로젝트는 Java 21·Spring Boot를 사용한다. 판매자 API용 코드는 기존 `infra/product` 매입처 조회와 구분한 `infra/market` 패키지로 두는 방안을 권한다.

| 책임 | 최소 기능 |
|---|---|
| NaverCommerceClient | 토큰 발급·캐시, 상품 목록, 상세 1건 |
| CoupangSellerClient | 최종 경로/query 기반 서명, 목록, 상세 1건 |
| EsmSellerClient | 공통 JWT, G/A별 목록, 상세 1건 |
| 실행 진입점 | 명시적으로 선택한 마켓의 소량 조회. 앱 시작 시 자동 호출하지 않음 |
| 결과 | 마켓·계정 별칭·요청 경로·HTTP·업무 결과·상품 수·다음 페이지 여부·소요 시간 |

처음에는 명시적 실행 명령으로 서버 Java 클라이언트의 요청을 검증해도 된다. 관리자 화면이 필요하면 기존 인증·최신 계정 검사·`ApiResponse` 규칙을 따르되, 외부 HTTP 상태를 내부 200 응답과 따로 기록한다. 내부 연결 작업 이력을 저장하는 경우 기존 CSRF·감사 방식도 적용한다.

큰 판매 마켓 모델·자동 매핑·예약 작업·양방향 동기화는 첫 조회 성공 이후로 둔다. 이 단계에서는 `ProductStore`, `InventoryService`, 최신화·상태 복구·선정 로직을 호출해 응답을 저장하지 않는다. 필요한 기존 설계는 [상품 조회](../product-lookup.md), [재고](../inventory.md)를 참고한다.

## 공통 요청·응답 처리

1. 연결 설정을 검증하고 제한된 페이지 크기 10으로 요청한다.
2. HTTP 연결뿐 아니라 **본문 수신 완료까지 전체 기한**과 응답 크기 제한을 둔다. 스트림이 멈추거나 취소되면 자원을 닫는다.
3. 최종 전송 URL·본문을 먼저 구성한다. 서명 대상과 실제 요청이 달라지지 않게 한다.
4. HTTP 상태 → JSON 파싱 → API별 업무 성공 → 필수 구조 → 계정·사이트의 순서로 검증한다. HTML 차단 페이지와 JSON 오류를 구분한다.
5. 타임아웃·5xx·호출 제한만 제한된 재시도를 고려한다. 인증·권한·잘못된 파라미터는 중단해 확인한다. 재시도마다 필요한 서명을 다시 만든다.
6. 토큰 캐시·호출 제한은 판매자 연결별로 관리한다. ESM은 확인 전까지 G/A가 같은 제한을 공유한다고 보수적으로 처리한다.
7. 외부 ID를 JavaScript Number로 변환하지 않는다. JSON 숫자 ID는 정확히 읽고 외부 DTO 경계에서 문자열로 만든다. 금액은 BigDecimal 등 정확한 타입으로 읽고, 원 단위 정책을 확인한 뒤 정규화한다.
8. 알 수 없는 추가 필드는 허용하되 성공 판정에 필요한 구조가 없으면 실패로 기록한다. 누락 수량·가격을 0으로 바꾸지 않는다.

로그에는 키·토큰·Authorization·서명·토큰 발급 폼을 출력하지 않는다. 안전하게 정리한 HTTP 상태·업무 코드·추적 ID·시간·상품 개수만 남긴다. 원본 증거가 필요하면 먼저 민감 필드를 제거한다.

검색용 POST도 외부 상품을 변경하지 않는 API다. 네이버·ESM 목록 POST를 판매 상품 등록 API와 혼동하지 않는다. 반대로 GET 성공만 확인한 상태를 전체 동기화 성공이라고 표시하지 않는다.

## 성공 판정

| 대상 | 정상으로 볼 최소 조건 |
|---|---|
| 네이버 토큰 | HTTP 200, 비어 있지 않은 access_token, 유효한 expires_in |
| 네이버 목록 | HTTP 200, contents 배열·페이지 구조 확인 |
| 쿠팡 목록 | HTTP 200, code=SUCCESS, data 배열·nextToken 규격 확인 |
| ESM 목록 | HTTP 200, items 배열·totalItems·페이지 구조 확인, 오류 본문 없음 |
| 네 마켓 각각 | 알고 있는 판매 상품 1건과 판매자센터 정보·ID 일치, 상세 조회 성공 |

빈 계정에서 정상 빈 배열을 받으면 **연결 성공 / 상품 일치 검증 미완료**로 구분한다. HTTP 200만 받고 업무 ERROR이거나 엉뚱한 사이트 상품이면 첫 목표도 완료로 표시하지 않는다.

## 필요한 검증만 유지

첫 구현에서는 서명 대상 문자열·폼 인코딩, 정상/오류/빈 응답, 큰 ID·정확한 금액, 시간 초과·취소·인증 정보 로그 비노출을 로컬 fixture로 검증한다. 실제 계정 호출은 명시적 실행에만 포함하고 일반 CI에서 자동 호출하지 않는다. 문서 정리 단계에는 서비스 테스트를 새로 추가하지 않는다.

## 조회 다음 단계의 연쇄 영향

- **조회 저장:** 판매 마켓·판매자·외부 번호 종류를 보존하는 별도 구조가 필요하다. 응답을 기존 매입처 선정으로 저장하지 않는다.
- **상품 연결:** 내부 상품 하나에 여러 채널·옵션이 연결될 수 있다. 코드·옵션 일치 확인과 수동 해제가 필요하다.
- **주기적 수집:** 페이지 순회 중 추가·삭제로 누락/중복될 수 있다. 응답에 없는 상품을 한 번의 실패나 일부 페이지 결과만으로 삭제하지 않는다. 목록 전체 완료와 최근 성공 시각을 구분한다.
- **재고 동기화:** 실제 보유와 채널 판매 가능 수량, 판매 예약·배분을 먼저 정의한다. 네 마켓에 동일 보유 수량을 그대로 올리면 동시 판매가 가능하므로 자동 동기화 정책이 필요하다.
- **판매 주문:** 매입 주문과 판매 주문은 다른 개념이다. 마켓 판매 주문 ID·옵션 매핑·중복 수집 방지·출고/고객 반품 기준이 있어야 물리 재고를 변경할 수 있다.
- **수정 요청:** 조회용 DTO를 그대로 상품 수정에 사용하지 않는다. 승인·비동기 작업·사이트 동시 적용·부분 성공을 고려한 별도 작업이 필요하다.
- **상품 통합·삭제:** 판매글과 내부 상품 연결의 이전·해제 정책을 정한다. 내부 상품 삭제가 외부 판매글 삭제가 되지 않게 한다.
- **가격:** 외부 판매가·할인가와 내 매입 단가를 별도로 유지한다. 배송비·수수료·정산·수익 계산은 판매 조회만으로 확정할 수 없다.

이 항목은 첫 조회를 막는 선행 구현 목록이 아니라, 다음 동기화 설계를 할 때 결정해야 할 과제다.
