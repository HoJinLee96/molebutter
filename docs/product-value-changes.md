# 가격·재고 변동과 팀 공통 검토

> 문서 유형: 현재 구현 안내. 2026-10-05 로컬 코드와 대조했다. 날짜가 붙은 적용·검증 문단은 당시 기록이며 현재 정책과 구분한다.

## 기준

판매글 ID, 실제 매장/채널 연결, 옵션 ID + stockScope가 같은 관측만 비교한다. 기본값은 마지막 확인 완료 시의 값이며, 최신화마다 기준을 이동하지 않는다. 현재 값이 기준으로 돌아오면 배지와 변동 필터에서 빠지지만 중간 이력은 남는다. 가격과 배송비는 따로 비교하고 재고를 판매량으로 해석하거나 여러 판매글에서 합산하지 않는다.

미조회/실패/수량 미제공은 0이 아니다. 확인 완료에서도 마지막 정상 기준과 그 필드의 확인 시각을 유지한다. 단순 전체 재고와 옵션별 재고는 다른 범위로 취급한다. 옵션 ID 변경에는 증감 대신 구성 변경을 표시한다. 부분 응답에서 빠진 옵션은 삭제/품절로 보지 않는다.

품절에서 양수 재고와 구매 가능이 확인된 경우 재입고를 표시한다. 구매 불가는 품절과 구분한다. 조회 건강 상태는 변동과 독립적이다.

## 저장과 동시 처리

V20은 관측(`product_value_observation`), 검토 기준(`product_change_review`), 현재 요약(`product_change_summary`)을 만든다. `procurement_product.change_version`은 조회 기준을 초기화해도 계속 증가하여 예전 화면의 확인 요청이 새 비교 구간과 우연히 같은 버전을 갖지 않도록 한다.

자동 조회 결과 및 개별 재고 조회의 확정 트랜잭션에서 관측/요약을 함께 저장한다. catalog 일관성 가드의 공유 잠금과 작업 점유권을 사용하며, 자동 조회 완료 상태와 관측의 `(origin_product_id,lookup_revision,supplier_id,source_key)` 유일 제약으로 재처리 중복을 막는다. 수동 조회는 기존 가격/배송비와 확인 시각을 그대로 가져온다. 실행별 상세 캐시도 최초 실제 응답 시각을 유지한다.

선정, 선호, 수동 매장 지정, 조회 시작/취소는 요약과 검토 버전을 갱신한다. 진행 중인 자동/개별 조회가 있거나 화면 버전이 다르면 확인 완료를 거절한다. 검색 기준 변경은 새 비교 구간을 시작한다. 상품 통합 시 과거 기록의 원본 상품 ID와 판매글 ID를 보존하며 새 기준에서 비교를 시작한다.

원본 검색 캐시에 `searchKeys`를 보존한다. 정상 종료된 검색 원본에 없는 기존 글만 미발견으로 분류한다. 상세 후보 제외/추천 한도/대표 재고 생략은 미발견으로 만들지 않는다. 과거 캐시처럼 원본 검색 식별 근거가 없으면 미발견을 추정하지 않는다.

## API와 화면

- 상품 목록 `change=ALL|SELECTED|ANY`, 응답의 `changes`.
- `GET /api/products/change-counts?q=&mode=ALL&status=`: 기존 목록 조건에 맞는 선정/전체 변동 건수.
- 상품 상세 최상위 `changes`와 비교 API의 `changes`: 개별 증감, 매장 최저가 교체, 저렴한 대안, 신규/미발견, 검토 기준.
- `GET /api/products/{id}/changes?kind=ALL|PRICE|DELIVERY|STOCK|STATE|REVIEW&supplier=&page=0`: 20건 단위 이력. 원본 상품 ID를 포함한다.
- `POST /api/products/{id}/change-reviews` `{ "version": 2 }`: 관리자/상품 담당자, CSRF, 감사 기록, 전용 버전 검사.

배지는 클릭해서 이전값/시각을 확인할 수 있다. 가격 상승 빨강/하락 파랑, 수량 증감 중립색, 품절/재입고 별도 표시다. 여러 옵션은 합계 대신 변동 옵션 건수를 표시한다. 확인 완료 후 필터와 배지는 정리되지만 이력은 유지한다. 매장 최저 검색가와 개별 가격 변화는 별도 표시한다.

더 저렴한 대안은 현재 선정가가 확인되고, 기존 선정 조건을 만족하며, 1,000원 이상 저렴하고 명시적인 양수 구매 가능 재고가 있는 글만 제공한다. 배송비는 별도다. 선정 변경이나 외부 판매 채널 반영을 자동 수행하지 않는다.

## 배포와 초기화

서버 재시작 시 Flyway V20 적용 뒤 `ProductChangeInitializer`가 현재 연결이 확인된 저장 결과를 읽기 전용으로 먼저 검사하고 `CHANGE_BASELINE_PREVIEW`를 기록한다. 그 목록을 상품별 짧은 트랜잭션에서 버전/진행 작업/기존 기준 존재 여부를 재검사하여 초기화하고 `CHANGE_BASELINE_APPLIED` 건수를 기록한다. `product.changes.initialize-enabled=false`로 시작 시 초기화를 비활성화할 수 있다.

진행 중 상품은 건너뛴다. 기존 기준이 없는 상품은 다음 최신화 직전 또는 첫 정상 결과에서 안전하게 기준을 만든다. 초기 검토 종류는 `SYSTEM_INITIAL`이며 사용자 확인과 구분된다. 기존 가격, 재고, 선정, 확인 시각, 과거 이력은 변경하지 않는다. 새 관측은 자동 만료시키지 않는다.

이 변경은 추가 네이버 검색/재고 요청을 만들지 않는다. 검색 최대 3페이지, 완료 후 30초 대기, 로그인 재개, 대표 재고 생략, 추천 한도/접속 제한 정책은 그대로다.

## 검증

- 격리 MySQL/Redis: ProductFlowIT 및 MigrationUpgradeIT. 기준 유지/복귀, 미확인 값 보존, 중복 처리, 동시 확인, 권한/CSRF, 초기화, 선호/선정/검색 기준 변경, 통합 출처 보존, 개별 재고의 가격 시각 보존.
- ProductChangePolicyTest: 옵션 동일성/범위, 부분 응답, 품절/재입고, 필드별 확인 시각.
- SupplierGroupStockTest: 실행별 캐시 시각 및 수동 조회 무효화.
- 변동 계산·필터·이력·확인·충돌은 Java·JavaScript 회귀 테스트에서 검증한다. 별도 변동 UI 스크립트는 유지하지 않는다. 실행 방법은 [테스트 안내](testing.md)를 따른다.
