# 공통 네비게이션과 설정

> 문서 유형: 현재 구현 안내. 2026-10-05 로컬 코드와 대조했다. 날짜가 붙은 적용·검증 문단은 당시 기록이며 현재 정책과 구분한다.

로그인 후 사이드바는 홈 / 상품 업무 / 근태 / 운영 관리 / 설정으로 구분합니다. 계정 역할에 허용된 메뉴만 표시하고, 로그인 후 홈 이동을 유지합니다. 상품 메뉴는 검색 조건 없는 `/products`로 진입해 전체 상품을 기본 100개씩 즉시 조회합니다.

`/settings?tab=brands|preferred|suppliers|payment-methods|schedule`로 설정 탭에 직접 접근합니다.

- 관리자: 브랜드·매장 등록과 수정·미사용 삭제, 공통 선호 매입처 관리, 결제 수단 관리, 자동 실행 설정 변경.
- 상품 담당자: 설정 조회, 상품에서 등록 브랜드 선택. 공통 설정 변경은 서버에서도 차단합니다.
- 조회 전용: 설정 페이지·API·상품 기능 접근 불가.

브랜드는 상품 등록 전에 추가할 수 있고 미지정도 허용합니다. 삭제·통합 후 보관 중인 상품까지 사용 개수에 포함합니다. 사용 상품이 있으면 브랜드를 삭제할 수 없습니다. 이름 변경은 표시명과 수정 버전만 바꾸며 조회 결과·조회 기준 버전은 유지합니다. 잡화 코드 규칙은 이름 문자열 대신 브랜드 ID에 연결됩니다.

엑셀 등록명에서 등록된 브랜드 하나가 명확히 확인되는 경우만 미지정 상품에 지정합니다. 예를 들어 등록 브랜드가 `헤지스`라면 `[헤지스] 가방`은 지정하고 `헤지스풍 가방`은 추정하지 않습니다. 서로 다른 등록명의 브랜드가 충돌하면 수동 지정 대상으로 남깁니다. 목록의 브랜드 자동 판단으로 기존 참고명을 재검사할 수 있습니다. 기존 지정 브랜드는 덮어쓰지 않습니다.

매입처 지원은 공통 설정에서 실제 `ProductSourceMetadata` 목록을 표시합니다. 이름만 추가해 기능이 활성화되는 설정은 없습니다.

선호 매입처는 `/settings?tab=preferred`에서 관리합니다. 현재 지원하는 쇼핑몰만 선택할 수 있으며 쇼핑몰 전체 또는 등록된 특정 매장을 허용합니다. 초기 목록은 비어 있고 등록 전에는 최신화를 실행하지 않습니다. 매장 ID는 이름 변경 후에도 유지하며 과거 이름은 자동 판별용 별칭으로 남깁니다. 사용 중인 매장은 삭제할 수 없습니다.

기존 데이터에는 지점·온라인 매장·판매자 종류가 남아 있습니다. 현재 새 매장 입력은 백화점·지점명 중심이며 일반 판매자 주소 입력은 제공하지 않습니다. 공식몰은 별도 상품 링크 확인·등록 흐름을 사용하고 확인된 WINDOW 채널만 허용합니다([채널 정책](naver-channel-policy.md)). 기존 종류·식별자는 호환을 위해 보존합니다. 확인된 지점은 조회 과정에서 목록에 추가될 수 있지만, 특정 매장의 선호 허용을 자동 추가하지는 않습니다. 매장 미확인 판매글은 상품 상세에서 해당 판매글에만 수동 지정할 수 있습니다.

## 결제 수단

ADMIN만 결제 수단 탭과 API를 사용할 수 있습니다. 신규 설치에는 카드·계좌이체·현금을 제공합니다. GET `/api/settings/payment-methods`, POST 추가, POST `/{id}` 이름 수정, POST `/{id}/delete` 삭제를 사용하며 수정·삭제에는 버전 검사가 적용됩니다. 삭제한 수단은 신규 선택에서 제외합니다. 주문은 수단 ID와 당시 이름을 보존하므로 이름 변경·삭제가 과거 주문 표시를 바꾸지 않습니다. 기존 자유 입력 결제 정보도 유지합니다([재고](inventory.md)).

## 예약·공통 API와 화면

자동 최신화는 한국 시간 기준 실행 여부와 시각을 관리합니다. 신규 기본값은 매일 18:00이며 기존 예약은 보존합니다. 변경한 설정은 다음 일괄 실행부터 적용하고 진행 중 작업은 유지합니다.

API는 `/api/settings/preferred-suppliers`, `/api/settings/supplier-stores`, `/api/settings/brands`, 관리자 전용 `/api/settings/payment-methods`, 읽기 전용 `/api/settings/suppliers`, `/api/product-refresh/settings`입니다. 기존 `/api/products/brands`도 등록부를 조회합니다. 변경 요청은 관리자·최신 계정·CSRF·감사·버전 충돌 검사를 적용합니다.

넓은 화면에서는 공통 사이드바와 본문 여백을 사용합니다. 표 화면은 남은 폭을 활용하며 설정 폼은 좁게 유지합니다. 좁은 화면에서는 메뉴 버튼·배경 클릭·Esc·포커스 순환으로 여닫는 메뉴를 사용합니다. 넓은 표만 가로 스크롤하고 모달은 화면 안에서 세로 스크롤합니다.

데이터 전환과 검증은 [상품 조회 안내](product-lookup.md)를 참고하세요.


### 과거 판별 구조와 기존 데이터 호환(V13)

당시 판매자 주소 등록 방식은 현재 신규 입력 방식이 아니다. 아래 내용은 기존 매장의 종류와 외부 식별자를 유지하는 배경이다.

매장 등록에서 백화점명과 지점명을 구분합니다. 스마트스토어는 실제 판매자 주소 외에 백화점 지점도 등록할 수 있습니다. 자동 판별한 외부 식별자는 내부 매장 ID에 연결하므로 매장 표시명 변경 후에도 선호 목록과 선정이 유지됩니다.

기존 매장에 백화점명이 빠졌다면 이름 수정에서 보완합니다. 조회한 외부 지점이 기존 이름만 등록된 매장과 모호하게 겹치면 해당 쇼핑몰 편집 화면에 **매장 연결 확인**을 표시합니다. 관리자가 확인된 지점과 기존 매장을 선택해 연결하며, 다른 백화점·쇼핑몰·매장 종류에는 연결할 수 없습니다. 다음 상품 조회부터 적용합니다. 상품 담당자는 목록만 조회합니다.


### 선호 매입처 등록 통합

설정에는 쇼핑몰당 한 행만 표시합니다. `선호 매입처 추가` 또는 `수정`에서 전체 / 특정 매장만 중 하나를 선택합니다. 특정 매장은 해당 쇼핑몰의 전체 매장 목록에서 여러 곳을 선택하며, 없는 매장은 같은 창에서 입력한 뒤 `매장 등록`을 누릅니다. 매장은 기존 매장 목록에 등록되며 자동 선택하지 않습니다. 목록에서 직접 눌러 선택하고 마지막으로 선호 조건을 저장합니다. 등록된 매장은 선호 설정 창을 취소해도 유지됩니다. 전체 허용과 특정 매장은 동시에 저장하지 않습니다.

더현대Hi 지점은 현대백화점을 자동 지정하므로 지점명만 입력합니다. 스마트스토어 새 지점 등록은 백화점명·지점명을 입력하고, 롯데ON 백화점 지점도 백화점명을 입력합니다. 등록된 매장의 이름 수정·미사용 삭제는 선택창 안에서 처리합니다. 이름 변경 저장과 삭제는 독립적인 명시적 작업이며, 창을 취소해도 이미 저장한 이름 변경은 되돌리지 않습니다.

상품 상세의 `매장 지정`도 같은 선택창을 사용합니다. 상품 담당자는 기존 매장 지정만 가능하고 관리자는 새 매장 등록과 선택적인 `선호 매입처에도 추가`를 사용할 수 있습니다. 추가 체크는 기본 해제이며 전체 또는 해당 매장이 이미 허용돼 있으면 중복 추가하지 않습니다. 지정은 해당 판매글에만 적용하며 상품별 매입처 선정은 그대로 유지합니다. 상품코드 판별이 불명확한 판매글은 지점을 지정해도 별도로 확인해야 합니다.

GET `/api/settings/preferred-suppliers`는 기존 `revision/stores/rules`와 쇼핑몰별 `groups`를 반환합니다. 실행 스냅샷의 `Preferences` 저장 형식은 그대로 유지합니다.

- PUT `/api/settings/preferred-suppliers/{mall}`: `revision`, `scope`(ALL/STORES), `storeIds`, `newStores`. 전체는 매장 목록을 비워야 하며 특정은 한 곳 이상이어야 합니다.
- DELETE `/api/settings/preferred-suppliers/{mall}`: 설정 `revision`. 해당 쇼핑몰의 선호 규칙만 제거합니다.
- POST `/api/products/{id}/suppliers/{supplier}/store`: 기존 `revision/storeId`에 `newStore`, `addPreferred`, `preferenceRevision` 추가. 신규 매장과 기존 ID는 동시에 지정하지 않습니다. 신규 등록 또는 선호 추가 시 관리자와 설정 버전을 검사합니다.

각 API 요청은 단일 트랜잭션입니다. 화면의 매장 등록은 선호 저장과 독립적인 요청이며, 등록만으로 선호 조건이나 상품별 지정은 변경하지 않습니다. 버전 충돌 시 자동 재전송하지 않고 최신 정보를 보여준 뒤 재확인을 요구합니다. 기존 중복 전체/지점 규칙은 전체로 표시하며 다음 저장 때만 정리합니다. 새 마이그레이션이나 기존 상품·매장 ID 변경은 없습니다.


새 매장 등록에서는 매장 구분 선택을 제거하고 백화점 지점으로 등록합니다. 스마트스토어도 백화점 이름·지점 이름만 입력하며, 일반 판매자 주소나 온라인 매장 등록 입력은 제공하지 않습니다. 더현대Hi는 현대백화점 자동 지정과 지점 이름만 표시합니다. 기존 매장 종류·외부 식별자·선호 연결은 보존하며 과거 매장의 이름 수정 시 종류를 바꾸지 않습니다.

`새 매장 추가`와 이름 수정은 모달 내부의 별도 입력 화면으로 전환합니다. 입력 중에는 쇼핑몰·허용 범위·선택 목록·선호 저장 버튼을 숨기며, 등록 완료 또는 `뒤로`/Esc로 목록 화면에 돌아옵니다. 돌아와도 이전 매장 선택을 유지하고, 새로 등록한 매장은 자동 선택하지 않습니다.


### 과거 검증 기록: 선호 설정과 최신화 경량화 점검 (2026-09-27)

아래 외부 지원 범위와 확인 대기 설명은 당시 기준이다. 현재는 WINDOW 전용이며 V16 이후 `pending`·`excluded` 응답은 빈 배열로 유지한다.

- 쇼핑몰 허용 여부와 저장된 수동 매장 지정을 먼저 검사하여 비선호 대상의 상세 요청을 생략합니다. 상품명만으로 판별한 지점은 상세 정보와 충돌할 수 있으므로 상세 확인 후 최종 필터링합니다. 조회 실패·주소 확인 필요 경로에도 같은 지점 조건을 적용합니다.
- 스마트스토어 URL의 판매자 경로만으로 일반 판매자나 백화점 지점을 확정하지 않습니다. 확인되지 않은 글은 개별 확인 대기에 남기고, 확인된 백화점·지점만 선호 매장에 연결합니다. 스마트스토어 재고는 계속 별도 검증 대상입니다.
- 상세 응답 공유 캐시는 실행 단위로 분리하고 최근 400개까지만 보관합니다. 이 수는 전체 작업의 수집 제한이 아닙니다. 네이버 검색은 기존 최대 3페이지를 유지합니다.
- 상품 상세의 선호 설정 중복 조회, 같은 상품 결과 안에서 동일 매장 확인의 반복 처리, 상품 이미지의 반복 UPDATE를 줄였습니다. 설정 저장 후 목록 조회는 한 번만 실행하며 상품 담당자에게 불필요한 외부 식별자 연결 후보 조회를 하지 않습니다.
- 검증은 외부 응답을 대체한 테스트와 임시 MySQL에서 수행합니다. 실제 매입처의 응답 변화나 스마트스토어 재고 지원을 보장하는 검증은 아닙니다.

### 쇼핑몰별 지점 구분 (V14)

선호 매입처 편집의 `지점 구분 사용`은 쇼핑몰 전체/특정 매장 허용 범위와 별도의 설정입니다. LF몰·헤지스는 기본 끔, 나머지 지원 쇼핑몰은 기본 켬입니다. 관리자는 스위치를 변경하고 상품 담당자는 목록의 설정을 조회합니다. 끄면 매장 입력을 숨기고 최종 저장 시 전체 허용으로 정리합니다. 켜면 전체로 시작하며 필요한 경우 특정 매장을 선택합니다. 저장 전 취소는 반영되지 않습니다.

지점 구분을 끈 쇼핑몰은 상품 비교에서 쇼핑몰별로 묶이며 매장 ID 없이 판매글을 선정할 수 있습니다. 조회 기준 변경·비선호 제한은 유지합니다. 현재 SEARCH_RESULT 경로는 검색 결과를 기준으로 하며 상품코드 정확 일치를 자동 보장하지 않습니다. 과거 코드 검토 표시는 이전 결과의 읽기 호환입니다. 지점 구분이 켜진 쇼핑몰의 전체 허용은 지점 확인 생략을 뜻하지 않습니다. 현재 지점 미확인 글은 선정 조건을 충족하지 않습니다. V16 이후 비교 응답의 `pending`·`excluded`는 빈 배열이며 과거 확인 대기 정보는 이력에 보존합니다. 선정은 판매글별로 유지하고, 재고를 합산하거나 다른 최저가 글로 교체하지 않습니다.

V14의 `supplier_mall_policy`는 선호 목록 삭제와 무관하게 남습니다. 기존 매장·외부 식별자·수동 지정·상품별 선정·조회 이력은 보존합니다. 지점 구분을 껐다 켜도 기존 연결을 사용할 수 있습니다. 비교와 선정 조건은 현재 설정을 사용하되 가격 확인 시각·조회 기준 버전은 변경하지 않습니다. 최신화 작업은 시작 시 `branchRequirements`를 스냅샷에 넣고 재개해도 유지하며, 필드가 없는 과거 스냅샷은 모든 쇼핑몰의 지점 확인이 필요했던 기존 기준으로 해석합니다.

- 선호 조회 응답: 쇼핑몰별 `groups[].branchRequired`와 선호 등록 전에도 사용할 수 있는 `branchRequirements` 맵.
- 쇼핑몰별 PUT: `branchRequired` 추가. 생략하면 현재 설정 유지. 끔이면 매장 입력은 비워야 하고 범위는 전체로 저장합니다. 기존 개별 규칙 API도 끔인 쇼핑몰에 특정 매장 규칙을 추가할 수 없습니다.
- 판매글 응답: `branchRequired`, `selectable`, `selectionUnavailableReason`. 서버의 선정 API와 같은 조건을 사용합니다. 지점 구분이 없으면 `storeStatus=NOT_REQUIRED`이며 그룹 ID는 `mall:<쇼핑몰 코드>`, 그룹의 매장 값은 null입니다.

완전히 일치하는 코드의 `시즌 일치`와 정상 가격의 `이번 조회 가격` 문구는 숨깁니다. 과거 저장 결과에도 동일한 화면 표시 규칙을 적용하며 시즌/색상 차이·미표기와 가격 확인 실패·참고 이력 경고는 유지합니다.
