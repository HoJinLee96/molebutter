# 2026-10-20 V51 운영 적용

사용자의 명시적 V51 적용 요청과 IDE 앱 중지 확인 이후 **13:57~13:58 KST**에 실행했다. 앞선 [기능 구현 검증](2026-10-20-coupang-registration-prefill.md)과 구분되는 운영 DB 전환 기록이다.

## 백업과 사전 확인

- 8081 리스너 없음. 전송 단계·주문·쿠팡 상품 수집·매입 갱신의 QUEUED/RUNNING 작업 및 판매/주문/수집 활성 임대는 0건이었다.
- 운영 DB는 V50 성공, V51 미적용, 기본 테이블 83개였다.
- 복구 사본: `backups/coupang-v51-20261020T135707/`. 접근 권한을 제한하고 실행 설정의 내용·자격 증명을 출력하지 않은 채 보관했다. 기존 JAR, 검증된 V51 JAR, 현재 소스 스냅샷과 JAR SHA-256도 보관했다.
- 전용 이미지 24개는 `molebutter-app/data/coupang-assets`에 있었다. 저장소 루트 기준 기본 경로에는 없으므로 전환 프로세스에만 `COUPANG_ASSETS_DIRECTORY` 절대 경로를 지정했다. 실행 설정 파일은 수정하지 않았다.
- 검증된 별도 빌드 JAR로 `scripts/upgrade-coupang-registration.sh --apply .../database`를 실행했다. 웹 앱·워커를 기동하지 않고 실제 쿠팡/R2 사용 플래그도 비활성화했다.

## 실제 실행 결과

1. 전체 DB 덤프 `database/database.sql` **530,955,217바이트**를 생성했다.
2. 별도 임시 MySQL의 격리 DB로 전체 덤프를 복원했다. 원본의 모든 기본 테이블에 대해 행 수와 전체 필드의 SHA-256 지문이 복원본과 일치했다.
3. 이미지 24개를 `database/sales-assets/`로 복사하고 파일 바이트 지문을 대조했다. 백업 중 운영 DB와 이미지가 변하지 않았음도 확인했다.
4. 그 뒤에만 V51을 적용했다. 새 `coupang_registration_defaults` 테이블은 **0행**이며 자동 기본설정 행을 만들지 않았다.
5. 적용 후 기본 테이블은 84개다. 기존 83개 중 Flyway 이력을 제외한 **82개 테이블의 행 수·전체 값 지문이 동일**하다. 기존 실행 미리보기 증거와 이미지 24개도 동일하다. 기존 V1~V50을 수정하거나 repair하지 않았다.
6. 별도 읽기 전용 최종 조회에서 V51 성공 이력 1건, 새 테이블 0행, 이미지 참조 24/24개 존재, 활성 작업·임대 0건을 재확인했다. 8081 리스너는 여전히 없다.

완료 표식은 `database/UPGRADE_COMPLETE`, 전후 지문은 `database/verified-before.txt`·`verified-after.txt`, 최종 상태는 `post-status.txt`, 백업 파일 지문은 `backup-sha256.json`에 있다. 백업에는 개인정보·비밀 설정이 포함될 수 있으므로 Git에 포함하거나 공개하지 않는다. 격리 복원용 임시 MySQL은 명령 종료 시 정리했으며 영구 백업은 보존했다.

앱은 중지 상태로 유지했다. 실제 쿠팡 상품값·R2 객체는 변경하지 않았다. 기능의 실제 계정 전송·직사각형 이미지 수용 검증은 이번 DB 적용 범위에 포함하지 않는다.
