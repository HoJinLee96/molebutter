# 쿠팡 목록·추천 조회 비용 개선 검증 (2026-10-17)

## 변경과 정확도

- 목록 프로젝션에서 표시할 상품·옵션을 한 번에 읽는다. 기존 옵션별 `SELECT *` 상품 재조회와 상세·쿠팡 원문 전송을 제거했다. 추천 목록도 페이지 키를 한 번에 상세화한다.
- 추천 후보와 같은 코드의 활성 쿠팡 옵션 수를 하나의 가벼운 조회에서 판독한다. 코드별 내부 상품 중복 수는 이진 정규화 코드로 묶어 집계하며 활성·삭제·병합 제외 기준을 유지한다.
- 선정 매입처의 최신화 전문은 사용하지 않고 SQL의 NULL 여부만 판독한다. 기존 선정·가격·재고·미발견·매장 식별 판단은 그대로 사용한다.
- 이전 정상 재고는 상품별 `(product_id,id)` 인덱스로 ID 역순 20건씩 이어 읽는다. 최대 100상품 단위로 묶고 동일 선정 판매글의 일치·상태·옵션 JSON만 전송한다. 정상값 판단은 기존 Java 판정식을 재사용한다. 대소문자·전체 식별자·중복 정상 관측·미확인 옵션·전체 옵션 수·확인 시각을 유지한다.
- 추천 공식·사유·계정 전체 건수·검색·유형·정렬·페이징은 변경하지 않았다. 요청 시점의 읽기 전용 트랜잭션을 유지하고 시간 기반 캐시·새 테이블·마이그레이션·인덱스·외부 요청은 추가하지 않았다.

## 실행 결과

- `./mvnw -o -Dmolebutter.build-directory=target/performance verify`: Java 742개 통과, 실패·오류·생략 0.
- JavaScript 전체 237개 통과.
- 임시 MySQL·Redis에서 ProductFlowIT 124개, CoupangRegisteredProductsIT 14개, CoupangWorkingCopyFlowIT 18개, 합계 156개 통과. 일반 상품·선정·추천·빠른 수정·단일 항목 전송 보호의 기존 회귀를 포함한다.
- 최종 SQL 계측을 보완한 목록 비용 검사 1개 추가 재실행 통과. prepared statement와 일반 statement를 모두 센다. 모의 매입처 포트로 전체 110옵션을 판정할 때 20/100개 페이지의 일반 목록 SQL은 각각 6/6회, 추천 목록은 5/5회였다. 매입·재고 어댑터 내부 SQL은 이 수치에 포함하지 않는다. 페이지 크기에 따른 행별 상품 조회가 없음을 검사하고 가벼운 프로젝션을 기존 전체 상품 판독 결과와 대조했다.
- 3상품·다중 페이지의 합성 이력에서 기존 판독기의 결과와 옵션·이전 여부·시각이 일치했다. 이전 재고 144, 정상 재고 0, 정상 근거 없음, 다른 판매글, 대소문자 불일치, 중복 정상 관측, 검토 대상 코드와 일부 미확인 옵션을 포함한다. 판독한 전문은 6,818,488문자에서 44,667문자로 약 99.3% 줄었다. 문자 수 감소이며 운영 응답시간의 개선율을 뜻하지 않는다.
- 103상품의 코드 조회·이전 재고 배치 경계와 새 정상 가격·재고가 바로 다음 요청에 반영되는 것을 검사했다. 기존 추천 전체·유형별 중복 집계·검색 후 페이징·등록일 정렬·조회 실패 회귀가 통과했다.
- 실제 렌더링 템플릿과 로컬 모의 API로 추천·매입처 펼침 1920/1440/1024/390px, 일괄 수정 1920/1440/390px 회귀 통과. 외부 트래픽은 차단했다.
- `git diff --check` 통과.

초기 비용 계측은 prepared statement만 세어 일반 설정 조회 1회를 누락했다. 위 수치는 최종 보완 계측 결과다. 운영 데이터의 응답시간은 측정하지 않았다. 전체 계정 판정과 필요한 과거 이력 탐색은 계속 수행하므로 데이터 규모와 이력 깊이에 따른 비용은 남는다.

실행 중인 IDE 앱·운영 DB·실제 쿠팡 판매값을 변경하지 않았다. Maven 출력은 별도 `target/performance`·`target/verification`을 사용했고 통합 검사는 임시 서비스와 합성 데이터만 사용했다.
