# 일괄 수정의 쿠팡 중복 조회 정리 검증 (2026-10-17)

## 변경

- 일괄 모달의 초기 표시와 저장 준비는 DB 관측을 사용한다. 기존 옵션별 원격 편집 조회와 준비 단계의 원격 재조회를 제거했다. 단일 빠른 수정의 기존 진입 경로는 유지한다.
- 상품별 `bulk-edit/context`로 같은 상품의 옵션을 한 관측·세션으로 묶는다. 선정 근거는 같은 내부 상품당 한 번 읽고 공통 편집 문서·설정·등록상품 문맥은 응답에 한 번만 제공한다. 서로 다른 상품의 초기 DB 요청은 최대 4개씩 처리한다. 닫힘·중단·재진입 이후의 응답은 무시한다.
- `bulk-edit/options/{vendor}/prepare`는 서버 세션의 DB 관측으로 해당 옵션의 가격 또는 수량 하나만 준비한다. 계정·매핑·revision·관측 버전·설정·선정 근거·준비 범위 검증과 다른 수정 의도 보존은 유지한다. 초기 문맥은 수정 의도와 전송을 만들지 않는다.
- 실제 전송 직전에 최신 상품·대상 옵션 판매값을 조회한다. 선택 항목의 기준값이 바뀌었거나 판매자상품코드가 정규화 후 달라지면 쓰기를 차단한다. 이미 원하는 값이면 재전송하지 않는다. 전송 후 반영 확인과 ACCEPTED/UNKNOWN 복구는 유지한다. 최신 확인은 각 실제 전송 직전에 수행하므로, 앞선 옵션 전송 전에 읽은 외부 값을 다음 전송에 재사용하지 않는다.
- 같은 상품의 앞선 옵션이 성공한 revision·appliedRevision과 일치하고 다음 옵션의 값·식별자·근거·설정이 그대로인 경우에만 이어 처리한다. 다른 수정의 revision 변경은 재확인을 요구한다. 실행 식별자·중복 방지 키는 전송 전에 보관한다.
- 기존 실행 API·저장 구조를 사용한다. 신규 일괄 문맥/준비 HTTP 경로를 추가했으며 새 테이블·마이그레이션·외부 일괄 쓰기 API는 없다.

- Java 전체 `verify`: 744개 통과, 실패·오류·생략 0. 별도 `target/bulk-performance` 출력 사용.
- JavaScript 전체 240개 통과. DB 묶음 문맥, 같은 상품의 성공 후 이어 처리, 외부 revision·설정 변경, 충돌·UNKNOWN 후 중단, 입력·의도적 빈칸 보존, 지연 응답, 기존 응답 유실·중복 클릭·재진입 복구를 포함한다.
- 임시 MySQL·Redis에서 CoupangWorkingCopyFlowIT 19개와 CoupangRegisteredProductsIT 14개, 합계 33개 통과. 두 옵션의 공통 세션·미저장 매핑 재사용, 초기 외부 편집 조회 0·작업본 수정 의도 미생성, 다른 수정 보존, 단일 항목 준비·중복 실행 키와 성공한 의도만 제거를 검사했다. 합성 판매자 ID와 비어 있는 외부 자격 증명을 사용했다.
- 모의 클라이언트에서 DB 단일 항목 준비의 원격 읽기·쓰기 0회를 확인했다. 정상 가격 실행은 전송 직전 상품 1회·대상 재고/가격 1회, 반영 확인 대상 재고/가격 1회와 PUT 1회였다. 실제 오류·재시도·후속 결과 확인에서는 호출 수가 달라질 수 있다.
- 최신 가격이 달라진 경우 및 판매자상품코드가 달라진 경우는 PUT 0회·실패·입력 보존, 수량 0이 이미 반영된 경우는 PUT 0회·반영 완료를 확인했다. 가격/수량 외 항목과 다중 수정의 DB 준비는 거절한다.
