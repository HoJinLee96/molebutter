# 승인 성공 후 자동 결과 조회 점검

확인일: 2026-10-21 한국 시각. 기존 앱 로그를 읽고 모의 API로 검사했다. 운영 DB·실행 중 IDE 앱·실제 쿠팡 상품값·R2 객체를 변경하지 않았다.

## 확인한 원인과 조치

- 실행 `900722435478292735`의 기존 로그에서 승인 PUT은 21:31:17.491에 성공했고 같은 WRITE 작업에서 상세 GET이 21:31:19.492에 자동 실행됐다. GET은 HTTP 400 `PRODUCT_PROCESSING`을 반환했고 21:31:21.878의 한 차례 재시도도 같은 오류였다. 자동 GET 누락이 아니라 조회 실패 후 접수 상태로 종료된 기록이다. 이후 RECONCILE 조회와 구분했다.
- 해당 로그 간격은 2,001ms이며 직전 [5초 변경](2026-10-21-coupang-create-five-second-gap.md)보다 앞선 기록이다. 읽기 전용으로 확인한 PID 7826의 시작 시각은 같은 날 18:51:12였다. 소스 수정만으로 실행 중 프로세스가 갱신됐다고 간주하지 않는다. 앱을 재시작하지 않았다.
- 현재 코드의 신규 등록 승인 성공→최초 자동 GET은 최소 5초다. 최초 승인과 승인만 재시도하는 경로 모두 같은 함수를 사용하며 추가 클릭을 요구하지 않는다. 자동 재시도와 일반 호출의 공통 2초 정책은 유지했다.
- 조회 실패가 `APPROVAL_PENDING`으로 기록되고 공개 메시지가 ‘등록 상품 확인 완료’로 치환되어 실제 조회 실패를 숨기는 표시 문제를 발견했다. 새 결과는 `APPROVAL_LOOKUP_PROCESSING`/`APPROVAL_LOOKUP_FAILED`로 구분해 자동 조회 실패를 표시한다. 상품을 실제로 읽어 승인 대기임을 확인한 `APPROVAL_PENDING`은 유지한다. 과거 기록은 변경하지 않는다.
- 새 결과도 ACCEPTED를 유지하므로 등록·승인 재전송을 막고 명시적인 결과 확인만 허용한다. 응답 본문·자격 증명·개인정보를 메시지로 복사하지 않는다. 새 테이블·마이그레이션은 없다.

## 검사 범위

- 실제 공통 클라이언트와 모의 HTTP 전송기로 규격 GET→등록 POST→승인 PUT→상세 GET의 정확한 순서·횟수와 두 응답 후 5초 간격을 검사한다.
- 승인 거절 뒤 승인만 재시도해 성공한 경우 상세 GET이 자동 실행되고 CREATE·상품코드 조회가 없는지 검사한다.
- 자동 GET의 상품 처리 중·통신 실패에서 접수·상품 ID 보존, 자동 조회 시도 안내와 공개 저장 메시지를 검사한다. 정상 조회의 승인 대기 표시와 구분한다.

## 실행 결과

- Java 21·오프라인 Maven의 분리 빌드 경로 `target/approval-auto-check`에서 `CoupangWorkingCopyWriteTest` 91개·`SubmissionWorkerDiagnosticsTest` 2개, 합계 93개 통과(실패·오류·생략 0). 모의 HTTP와 실제 대기에서 등록 응답→승인 PUT은 5,003ms, 승인 응답→자동 상세 GET은 5,005ms였다.
- `scripts/test-integration.sh -Dtest=CoupangWorkingCopyFlowIT -Dsurefire.failIfNoSpecifiedTests=false`: 임시 MySQL·Redis에서 33개 통과(실패·오류·생략 0). 종료 후 임시 서비스·DB는 정리했다. 전체 모듈 컴파일도 통과했다.
- 변경 범위 `git diff --check` 통과. 총 126개 검사이며 PC/모바일 화면 검사나 실계정 전송을 새로 수행하지 않았다. 앱 재시작 후 새 실행부터 변경 메시지를 사용한다.

## 후속 수정: 처리 중에도 자동 GET 계속

위 첫 수정은 자동 조회 실패의 표시만 보완했고 자동 흐름을 계속하라는 요청을 충족하지 못했다. 이후 사용자가 제공한 실행 `900726220278450344`의 로그에서 승인 성공 21:44:54.239 → 자동 GET 21:44:59.240(5,001ms)은 실행됐지만 처리 중 응답·HTTP 재시도 후 ACCEPTED로 끝나 수동 확인을 요구한 것을 확인했다.

- 신규 등록의 승인 PUT 성공 뒤 상품 처리 중 오류나 정상 상세 응답의 승인 대기 상태이면 GET만 5초 간격으로 계속한다. 최초 승인·승인 재시도 성공·기존 ACCEPTED 신규 승인 단계의 명시적 결과 확인에 같은 확인 함수를 사용한다. 등록 POST·승인 PUT·상품코드 조회·옵션 재고 조회는 추가하지 않는다.
- 전체 자동 확인은 단조 시계 기준 10분·최대 120회이며 각 GET의 기존 HTTP 재시도(2초)는 별도다. 네트워크/인증 오류·취소·권한 변경·승인 반려·식별자/옵션 연결 이상은 즉시 종료한다. 성공한 승인과 상품 ID는 ACCEPTED/CONFIRMED로 보존하며 조회 실패를 승인 실패로 바꾸지 않는다.
- 확인 동안 기존 실행 단계는 RUNNING을 유지한다. 화면은 ‘승인·결과 자동 확인 중’으로 표시하고 앱 상태 조회를 계속하며 수동 결과 확인·재전송을 제공하지 않는다. 계정 임대 heartbeat를 유지한다. 완료 시 기존 완료 처리를 사용한다. 10분 한도 종료는 `APPROVAL_CHECK_TIMEOUT`, 권한 변경은 `APPROVAL_CHECK_ACCESS_DENIED`로 구분한다. 앱 종료/중단의 UNKNOWN 보호는 유지한다.
- 새 엔드포인트·테이블·마이그레이션·주기 작업을 추가하지 않았다. 과거 ACCEPTED 결과를 DB에서 자동 재큐잉하지 않는다. 새 실행부터 적용하며 과거 ACCEPTED 결과 확인을 직접 실행하면 조회만 자동으로 이어간다. 실제 운영 앱은 재시작하지 않았다.

- Java 21·분리 빌드 `target/approval-poll-check`: `CoupangWorkingCopyWriteTest` 96개와 `SubmissionWorkerDiagnosticsTest` 2개, 합계 98개 통과. 처리 중 응답→승인 대기→승인 완료의 실제 공통 클라이언트/모의 HTTP 검사에서 반복 GET을 자동 수행하고 등록 POST·승인 PUT은 각각 한 번뿐이다. 각 자동 확인의 응답 후 간격은 5,002~5,003ms, 기존 HTTP 재시도는 2초 이상이었다. 처리 중 무한 응답의 120회 한도·권한 변경·인증/통신 실패·취소·ID 보존도 검사했다. 10분을 실제로 모두 기다린 검증은 아니며 모의 대기로 횟수 한도를 확인했다.
