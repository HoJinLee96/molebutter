# 네이버 보안 확인·418·429 자동 대기 검증

2026-10-19 사용자 요청에 따라 코드 변경과 격리 검증을 수행했다. 운영 DB·실행 중인 IDE 앱·검색 전용 브라우저·실제 네이버 응답·쿠팡 판매값은 변경하지 않았다. 새 엔드포인트·DB 마이그레이션·주기 작업은 없다.

## 동작

- HTTP 418·429는 기존 `ACCESS_RESTRICTED`와 실제 HTTP 상태를 함께 검사해 자동 대기에 포함한다. 보안 확인·자동입력 방지·접속 제한 HTML은 `SECURITY_CHECK`로 구분한다.
- 1~4번째 연속 실패에는 실패 시각부터 각각 5·30·60·120분 뒤를 예약한다. 5번째 실패에는 `BLOCKED`, 예정 시각 null, 공통 수동 재개 필요 상태로 멈춘다.
- 로그인·무요청·통신 실패와 같은 `search_retry_count`를 사용한다. 원인이 달라져도 성공 전에는 주기를 초기화하지 않는다. 정상 실제 검색 성공은 횟수를 초기화한다.
- 기존 HTTP 403, 상태 미확인 접속 제한, 로그인된 전용 세션, 탭 정리 실패·브라우저 실행 불가의 즉시 수동 확인은 유지한다. CAPTCHA 풀이·쿠키 삭제·로그인·대체 조회를 추가하지 않는다.
- 중복 실패·오래된 소유자 결과를 이중 집계하지 않는다. 예약 전 재개를 거부하고, 취소·새 작업으로 공통 휴식을 우회하지 못한다. 가격·재고 관측·선정 근거를 실패로 갱신하지 않는다.
- 화면에는 원인과 예정 시각을 표시한다. 보안 확인을 로그인으로 잘못 표시하지 않는다. 수동 중단과 사용자 일시 중단은 기존 규칙대로 유지한다.
- 기존 BLOCKED/PAUSED 작업을 소급 자동 재개하지 않는다. 변경 적용 뒤 기존 중단 작업은 사용자의 명시적 재개가 필요하다.

## 실행 결과

- 검색·매입 및 의존 모듈 `verify`: Java 202개, 실패·오류·생략 0. `target/naver-restriction-check`를 사용했다.
- `NaverSearchAccessTest`, `NaverSearchRecoveryBrowserTest`, `NaverGuestSearchTest`: HTTP 403/418/429·보안 HTML·로그인 리다이렉트·정상 응답을 검사했다. Chrome의 모든 URL은 모의 응답 또는 중단 처리하며 실제 네이버에 접근하지 않았다.
- 격리 MySQL·Redis의 `ProductFlowIT`: 129개, 실패·오류·생략 0. 418·429·SECURITY_CHECK 각각 5회 연속 실패, 네 개 예약 시각, 다섯 번째 수동 중단, 중복 실패 1회 집계, 조기 재개 거부, 장시간 후 자동 중단 유지, 명시적 재개 후 새 주기, 원인 혼합·성공 시 초기화, 취소·새 작업 우회 방지를 확인했다. 기존 상품 회귀도 함께 통과했다.
- JavaScript 264개 통과. 상품 상세의 보안 확인·접속 제한 대기 사유와 스피너 중단·폴링 유지를 검사했다.
- `scripts/test-naver-restriction-wait-ui.cjs`: 실제 프로젝트 HTML/JS/CSS와 모의 API로 1440/390px에서 자동 재개 대기·원인·예정 시각, 수동 재개 버튼 구분과 최종 중단을 검사했다. 쓰기 요청 0회. 화면은 `/tmp/naver-restriction-{wait,stop}-{1440,390}.png`에 저장한다.
- `git diff --check` 통과.

검증 로그는 `/tmp/molebutter-naver-restriction-{verify,it,js,ui}.log`에 남겼다. 초기 새 통합 테스트의 조기 재개 호출과 작업 완료 전이를 기존 서비스 계약에 맞게 고친 뒤 전체 129개를 재실행해 통과했다. 운영 설정·DB 레코드는 수정하지 않았으며 실행 중 앱을 빌드하거나 재시작하지 않았다.
