> 과거 실행 기록이다. 아래 건수·계약 확인·테스트 수치는 당시 결과이며 현재 검증 완료를 뜻하지 않는다. 현재 안내는 [쿠팡 주문](../coupang-api/sales-orders.md)을 따른다. 본문은 기존 안내에서 분리해 보존했다.

## 실제 계정 읽기 검증

2026-10-07 애플리케이션 런타임으로 최근 7일을 조회했다. 비밀 설정은 Spring이 로딩했으며 테스트 자료에 복사하지 않았다. 모든 아래 요청은 HTTP 200·업무 코드 200과 정상 목록 구조를 반환했다.

| 수집원 | 건수 | 다음 페이지 |
|---|---:|---|
| ACCEPT | 2 | 없음 |
| INSTRUCT | 6 | 없음 |
| DEPARTURE | 1 | 없음 |
| DELIVERING | 10 | 없음 |
| FINAL_DELIVERY | 12 | 없음 |
| NONE_TRACKING | 0 | 없음 |

| RETURN_UC | 2 | 없음 |

| WITHDRAWN | 1 | 없음 |

정상 주문의 건수는 정규화된 주문 그룹 수, 클레임은 항목 관측 수다. 합산한 고유 주문 수가 아니다. INSTRUCT를 페이지 크기 1로 별도 조회하여 첫 페이지 1건·다음 토큰 있음, 다음 페이지 1건·다음 토큰 있음도 확인했다.

반품·취소 목록은 `searchType`을 생략한 하루 구간 요청, CANCEL의 `orderId` 생략, 최상위 `nextToken` 계약이 실제 계정에서 확인됐다. 해당 목록 계약 게이트를 활성화하고 이 문서를 설정의 검증 근거로 연결했다. 교환은 정상 빈 목록만 확인했다. 추가 읽기 검증에서 반품 접수번호 단건 1건, 철회 이력 접수번호 POST 조회 1건, 기존 취소 접수의 최초 날짜 재조회 1건을 모두 HTTP 200·업무 코드 200으로 확인했다. 취소 재조회는 기존 접수번호가 응답에 존재함을 확인했으며 철회 POST도 기간 조회에서 받은 철회 접수번호의 일치를 확인했다. 비어 있지 않은 교환 응답과 교환 접수 갱신은 실제 계정에서 미검증이다.

실제 계정 쓰기·발주확인·송장등록·클레임 처리 요청은 실행하지 않았다.

## 자동 검증

Java 전체 회귀와 격리 MySQL·Redis 통합 테스트 결과는 [검증 기록](../testing.md)에 기록한다. 주문 전용 테스트는 페이지 실패·재개, UUID 멱등성, 완전 스냅샷 교체, 클레임만 있는 주문, 철회 반영, ADMIN 권한과 개인정보 미저장을 검사한다. 개선 후 Java 385개·JS 117개·실행된 통합 테스트 245개가 통과했다. 기존 자료 업그레이드와 주문 관련 15개 재실행도 통과했다. 합성 API를 사용한 브라우저 대표 흐름은 데스크톱 1440px·모바일 390px에서 localhost와 일반 내부 IP HTTP 모두 통과했다.

## 수동 수집 개선 (2026-10-07)

- 계정별 DB 잠금 행에서 작업 lease를 원자적으로 확보하고, 취소·재개·저장도 계정→작업 순서로 잠근다. 만료된 실행은 중단 처리하며 늦은 응답은 소유권 확인 후 저장한다.
- 목록 페이지 성공은 커서를 진행한다. 실패한 주문 상세만 별도 서버 작업으로 보관하고 재개하며 이미 성공한 목록·상세를 반복 호출하지 않는다.
- 수집 응답은 완료/전체 구간·실패 상세·주문/상품 행/클레임 접수/상품 미확인 수를 구분한다. 과거 이력의 건수는 현재 보존 자료에서 복원하고 `복원 수치`로 표시한다. 진행은 구간 기준이며 예상 시간·완료 시각을 추정하지 않는다.
- 안전한 실패 단계·오류 코드·수집원·조회 구간을 제공한다. 원문 응답·외부 예외 메시지·배송 개인정보는 실패 기록에 저장하지 않는다.
- 클레임 유형과 변경일 검색은 같은 클레임에 적용한다. 오래된 시각의 응답으로 최신 상태를 후퇴시키지 않는다. 시각을 확인하지 못하거나 동일 시각에서 상태가 충돌한 관측은 최신 미확인으로 구분한다.
- 상세 배송·상품은 방금 조회한 시각, 클레임은 저장된 관측 시각을 구분한다. 상세 닫기·이탈·브라우저 복원에서 개인정보를 제거하고 이력 선택·조회 지연에도 현재 화면을 보호한다.

실행·검증 결과는 [testing.md](../testing.md)의 개선 검증 기록을 따른다. 기본 최근 7일·최대 31일의 수동 수집을 유지하며 자동 수집과 나머지 마켓 연결은 추가하지 않는다.

## 취소·반품 발주서 거절 처리 (2026-10-07)

- HTTP 400 본문의 고정 `message`가 공식 SOURCE와 일치할 때만 `ORDER_UNAVAILABLE`, `ORDER_INVALID`, `ORDER_ACCOUNT_MISMATCH`로 분류한다. 불명확한 본문은 `ORDER_REJECTED`로 남긴다. HTTP 상태만으로 취소·반품을 판정하지 않으며 외부 원문·개인정보·인증값을 저장하거나 로그에 남기지 않는다.
- 확인된 취소·반품 제한은 발주서를 반복 호출하지 않는다. 같은 계정·주문의 클레임 관측이 있으면 `SKIPPED`, 근거 없는 제한·주문번호 오류·판매자 불일치·사유 미확인은 `BLOCKED`로 남긴다. 실패 재개는 이 항목을 자동 재요청하지 않는다. 판매자 불일치는 수집을 중단한다. 일시적 실패의 재개와 기존 429 대기·제한 재시도는 유지한다.
- 취소·반품 응답의 상품명·옵션명·상품/옵션/배송 ID·접수일·purchaseCount를 허용 목록으로 보존한다. 클레임 수량과 응답 주문 수량을 구분하며 금액·주문일·관리코드는 추정하지 않는다. 이전 JSON의 추가 필드는 null로 호환한다. 교환·철회에 다른 API의 필드를 대신 적용하지 않는다.
- 정상 상품과 발주서 미확보 주문의 건수를 구분한다. 제한된 주문 상세는 저장된 클레임을 보여주고 배송 개인정보 조회를 반복하지 않는다. 기존 정상 주문 관측은 별도 구역에 보존한다. 철회 관측은 제한 표시를 해제한다.
- 추가 V36은 안전한 사유 코드만 추가한다. V34·V35는 변경하지 않는다. 기존 일반 거절 8건을 일괄 취소·반품으로 판정하지 않는다. 앱 재기동 후 같은 기간을 새로 수집하면 상품 정보를 보강하고 사유를 다시 분류한다.

검증: 합성 응답으로 거절 사유·비노출, 클레임 정보·큰 ID·수량 구분, 재수집 시 제한 발주서 호출 생략, 주문번호 오류 재개 제외, 관리자 권한·마이그레이션·모듈 경계를 검사했다. JS와 1440px/390px 내부 IP에 준하는 HTTP 화면도 확인했다. 과거 8건의 거절 본문은 기존 코드가 버렸으므로 개별 사유와 운영 데이터 복구는 실계정 검증되지 않았다. 운영 앱 재기동·수집·커밋·배포는 수행하지 않았다.
